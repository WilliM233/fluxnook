# Fluxnook

A cozy place to keep your shelves: films, TV, books, comics and games in one nook, organized the way you read and watch them, with a journal for each pass through and the physical collection tracked alongside.

Volume 1 is in progress. Today you can sign in with a magic link, search TMDB for a film or a show, Open Library for a book (or type an ISBN), or Comic Vine for a comic series, and add films, shows and books to the catalog, add a comic series with all its issues, pick what a collected edition holds, add an item by hand, and open any item's page, locally. The nook lists your shelves and a shelf opens as a page of numbered works. You can make a shelf, and on its page add works from the catalog, make sections, drag works around, mark each Done or Skipped, rename, edit, remove and delete. You can also add a work to a shelf from its item page, and a whole comic series from its series page, or onto a new shelf made on the spot. An item page shows your reads of a work under Journal, and from it you log a read or a watch, rate it with stars, and add, edit and delete journal entries; the Journal page lists every entry you have written, newest first; a shelf shows the stars on its rows and the mean over them, and a work marked Done offers to log the read or watch; the same writes are in the API (`docs/API.md`). An item page's Editions section, on every type, lets you own a copy of a printing, or of a format the catalog doesn't list yet, and shows where a comic is owned through a collected edition; the copy routes are in the API too. A comic series page lets you tick each issue as a floppy you own, a shelf row marks what you own, and the ISBN card has an "and I own it" box. The Collection page lists every copy you hold, newest first, with a Shopping page beside it for what your shelves ask for and your copies don't answer, and a nook card says how many of its works you own.

## Run it locally

You need Node 22.15.0 and Docker Desktop, running. The Supabase CLI is a pinned devDependency, so `npm install` brings it; nothing to install globally. The commands below were run in Git Bash on Windows.

```sh
npm install
cp .env.example .env.local
npx supabase start
npm run dev
```

Open http://localhost:3000, enter any email address and press "Send me a link". No mail leaves your machine: it lands in Mailpit at http://127.0.0.1:54324. Click the link there, in the same browser, and you're on `/nook`. Asking for a link with a new address creates its account, before the link is clicked.

Things that trip people up:

- Use `localhost:3000`, not `127.0.0.1:3000`, and nothing else on port 3000. The link always returns to `http://localhost:3000` (`supabase/config.toml` `[auth]`), and the sign-in cookie lives on the host you asked from. From anywhere else the link won't sign you in.
- Every checkout of this repo has `project_id = "fluxnook"`, so they share one set of containers and one database. Run `npx supabase stop` in the other checkout before `npx supabase start` in this one. The second checkout starts on the first one's data.
- `.env.example` holds the Supabase CLI's fixed local URL, publishable key and database URL. Without `.env.local`, the app throws naming the missing variable.
- Two lines in `.env.example` are empty on purpose, and both are server-only: never `NEXT_PUBLIC_`, never committed, never in a response. `SUPABASE_SECRET_KEY` is the `SECRET_KEY` value `npx supabase status` prints (`npx supabase status -o env` prints it as `SECRET_KEY=`); the server writes cover images to Storage with it. Empty, an import still works and the item has no cover. `TMDB_API_KEY` is the v4 read access token from https://www.themoviedb.org/settings/api (a free TMDB account). Empty, search answers "Search isn't set up on this nook yet" and every other page works.
- Open Library needs no key, so book search works on a fresh clone. Three optional lines in `.env.example`, all empty: `OPENLIBRARY_BASE_URL` and `OPENLIBRARY_COVERS_BASE_URL` (empty means Open Library's own) and `OPENLIBRARY_CONTACT`, an email or URL that goes into the `User-Agent` (`Fluxnook/<version> (<contact, else the repo URL>)`) and nowhere else. `npm run openlibrary:stub -- --port 4011` serves the recordings in `tests/fixtures/openlibrary`, the ISBN redirect and a 1x1 jpg for every cover; point both URLs at `http://127.0.0.1:4011`. Playwright starts its own stub on 4011. Open Library allows 1 request a second anonymously and 3 with an identified `User-Agent`.
- Comic Vine needs a key: `COMICVINE_API_KEY`, from the API page of a Comic Vine account (https://comicvine.gamespot.com/api/). Empty, comic search answers "Comic search isn't set up on this nook yet" and every other page works. `COMICVINE_BASE_URL` (empty means Comic Vine's own) and `COMICVINE_CONTACT` (an email or URL for the `User-Agent`, `Fluxnook/<version> (<contact, else the repo URL>)`, and nowhere else) are optional. `npm run comicvine:stub -- --port 4012` serves the recordings in `tests/fixtures/comicvine` and a 1x1 jpg for every cover except one whose file name starts with `missing-`, which is a 404; `--dir <path>` serves a copy of the recordings instead. A volume whose issues have no recording is a 500 from the stub (the stub's terminal names the file), so an import of it answers 503, never an empty run. With `COMICVINE_API_KEY` set to any word, point `COMICVINE_BASE_URL` at `http://127.0.0.1:4012/api`. Playwright starts its own stub on 4012 and sets both. Comic Vine allows 200 requests per resource per hour and its terms are non-commercial.
- Tests and the Browse never need a TMDB key. `npm run tmdb:stub -- --port 4010` serves the recordings in `tests/fixtures/tmdb` and a 1x1 jpg for every poster. Point the app at it with `TMDB_BASE_URL=http://127.0.0.1:4010/3` and `TMDB_IMAGE_BASE_URL=http://127.0.0.1:4010/t/p` in `.env.local` (both optional; they default to TMDB's own). Playwright starts its own stub and sets these for the app it runs.

## Install on a phone

From 2.1.2 the device stub (`device/`) is built into an Android apk and a Windows installer by `.github/workflows/build.yml`. The app on either is still the stub: shelves and nothing else. The real nook comes with Ch 2.2.

Where the builds come from:

- Every pull request into `dev` or `main` runs `Build` and uploads two artifacts: `fluxnook-android` (`Fluxnook_<version>_<label>.apk`, arm64 only, Android 7.0 and up) and `fluxnook-windows` (`Fluxnook_<version>_x64-setup.exe`). `gh run download <run-id> -n fluxnook-android` fetches one. The label is the first seven characters of the PR's head commit, printed on the page under the version.
- A Volume or hotfix tag's Release gets the same two files attached. A chapter tag has no Release, so its builds are its run's artifacts.

On Android, with the phone on USB debugging and `adb` on PATH:

```sh
adb install Fluxnook_<version>_<label>.apk
adb install -r Fluxnook_<version>_<label>.apk
```

The first line is the first install only. Every build after it is the second line, over the one on the phone. Never uninstall to get past an error: read the error. The store lives inside the app.

Things that are one-way:

- **One keystore.** `~/.fluxnook-signing/fluxnook-upload.jks`, alias `upload`, made once on 2026-11-07 and held by L in a password manager. CI signs with it through the secrets `ANDROID_KEY_BASE64` and `ANDROID_KEY_PASSWORD`. Its certificate SHA-256 is `D7:FA:62:2B:A8:4E:32:5D:0D:3E:D0:8F:D3:4B:7E:98:94:CF:48:D3:1C:3E:7C:5F:E0:E0:6B:C7:99:00:52:1D`; `apksigner verify --print-certs <apk>` must print it. Android refuses an install-over signed by another key, so a lost or changed key is a wipe for every phone that has the app.
- **The identifier `app.fluxnook`, the scheme `useHttpsScheme: false`, the data name `idb://fluxnook` and the device person's id `00000000-0000-4000-8000-000000000001`.** Never change any of the four. The identifier and the scheme are in `src-tauri/tauri.conf.json`, the data name and the id in `device/db.ts`, and `tests/unit/shell-config.test.ts` and `tests/unit/rummage-device.test.ts` pin them. Moving one makes the app open an empty store with no error. Measured on Windows with the probe: the same data folder counted 3 under `http` and 1 under `https`.
- **PGlite across a Postgres major.** A store written by PGlite 0.4.6 (PostgreSQL 17.5) fails under 0.5.15 with `PGlite failed to initialize properly` and still opens under 0.4.6; a store written by 0.5.0 (18.3) opens under 0.5.15 (18.6). Measured in Node on directory stores; the IndexedDB case was not run. So the data refuses a bump that moves Postgres's major, undamaged. Such a bump needs a dump and a restore, never a plain version change.

The store is best effort. `navigator.storage.persist()` is refused in Android System WebView 156 and in WebView2 157, under both schemes (the probe's table, `docs/plans/2.1.2-builds.md` section 5), so a phone or PC short of space may evict it, and an evicted store opens as a first launch with no words. Ch 2.5's export is the backup.

Older builds are refused over newer ones:

- Android: `scripts/version-code.mjs` derives the apk's `versionCode` from `package.json`'s version, so a newer build always has the higher code. `0.2.0-ch.1.2` is 1990102, `0.2.0` is 2000000. A version outside the rule fails the build in words. Tauri's own default would give every `0.2.0-*` build 2000.
- Windows: `bundle.windows.allowDowngrades` is `false`. The NSIS installer won't install an older version over a newer one in silent, passive or update mode; the interactive installer only lets you after uninstalling the newer one first.

On Windows, `Fluxnook_<version>_x64-setup.exe` installs per user. The app is in `%LOCALAPPDATA%\Fluxnook` and the store is in `%LOCALAPPDATA%\app.fluxnook`, apart. Measured on the dev box: an installer run over an installed build kept a file placed in the store, and a silent uninstall removed the app and kept the store. The uninstaller you click through has a box, **Delete the application data**: ticked, it removes `%LOCALAPPDATA%\app.fluxnook`, which is the store, so leave it unticked (read from the installer script Tauri generates, `src-tauri/target/release/nsis/x64/installer.nsi`, not run). The installer isn't code-signed, so Windows may warn before it runs.

A local `tauri android` debug build is `app.fluxnook.debug`, a different app, so it can't install over the phone's. The apk is built by CI only; the dev box has no NDK. The build reads its own library and fails unless every `PT_LOAD` segment is aligned to 16 KB (`scripts/elf-load-align.mjs`), since a 16 KB-page Android can't load a 4 KB one.

## Screens

Every screen sits behind sign-in; a signed-out visit to any of them goes to `/`. The header links Search, Nook, Journal and Collection; the footer carries TMDB's required attribution line and logo, and a line each crediting Open Library and Comic Vine.

- `/search`: type two or more characters, pick All, Films, TV, Books or Comics. The URL carries `q` and `type`. Each result says one of three things. In your catalog: Open goes to the item. Looks like one you have: Add opens a sheet with the provider's side and the catalog item's side; "Same" adds the provider's source and fills what the item lacks, "Different, add as new" makes a second item. New: Add imports it and goes to its page. With the box empty it lists the 12 newest catalog items.
  - Books asks only Open Library. All asks TMDB and Open Library side by side and groups the rows by provider; if one doesn't answer, its group says so and the other still shows. A book matches on title and author, never year, because Open Library's first-publish year is often wrong; the looks-like line shows the catalog's own year.
  - Comics asks only Comic Vine, and All asks all three, in the order Films and TV, Books, Comic series. Each row is a Comic Vine volume: cover, name, start year, a Series pill, "<publisher> · <n> issues". The status line is one of: In your catalog, with Open going to `/series/<id>`; "Looks like one you have: <label>, <n> issues added by hand" for a hand-entered run; "Looks like one you have: <n> collected editions added by hand" for hand-entered collected editions; or nothing.
  - Add on a comic row (looks-like or new) opens the import sheet: Comic Vine's side, a "What are these?" choice of Single issues or Collected editions (Collected is preselected when the name holds collection, omnibus, compendium, library or trade; it brings a Format select, Hardcover first), and then one of two shapes. On a looks-like row the sheet shows the catalog's side. Same attaches Comic Vine's series and issues to the hand-entered run, matching each issue to yours by number; Different makes a second run. On a new row a "Same as a run you added by hand?" select lists every hand-entered run (and, under Collected, every stem of collected editions), No first. Add with a run picked imports at once. Add with No, when hand-entered runs exist, asks once: "Adds <n> comics as a new run beside the <m> runs you entered by hand. If it is one of them, pick it above. Add anyway?", with Add anyway and Cancel; Cancel returns to the sheet and imports nothing, and the next Add asks again. With no hand-entered run Add imports without asking. Either way you land on `/series/<id>`. A refusal (a run already attached to another volume, a run of the other form) shows in the sheet and writes nothing.
  - ISBN mode: when the box holds a valid ISBN-10 or ISBN-13 (hyphens and spaces allowed, check digit tested in the browser), the chips grey out and the page shows that one edition from Open Library: publisher, published, pages, both ISBNs, a Format select, and whether its work is in your catalog. "Add this edition" adds the work if it isn't there and the printing under it. Under the Format select, "and I own it" (off by default) makes one copy of that printing with the add, with no condition or note, and the add lands on the item page; it also works through the "Same" and "Different" sheet. A printing already in your catalog shows no box when you hold nothing of it; one you hold shows "In your collection" beside "This edition is in your catalog", and the box ticked and disabled. If the copy is refused after the printing went in, the card stays with "Added, but couldn't add your copy. Try again." and Add again makes one copy, not two. A bad check digit shows "That isn't a valid ISBN." and sends nothing.
- `/items/<uuid>`: the item page. Cover, facts for its type, summary, release date at the precision held, sources as links, relations in both directions, and your reads of it (see Journal below), and which of your shelves hold it (see On your shelves below). Every type has an Editions section (see Editions and copies below). A comic's pill row links its series and prints Vol. <n>, its kind and #<n>; the Series fact reads "<name>, Vol. <n> · #<n> of <count>" with links to the previous and next numbered issue; a Collected in section lists the editions whose contents hold it, each as "<Format> · <year> · with <the rest of the contents>" and ending in "Your copy" when you hold that edition or I own this when you don't (its note: "An edition whose contents hold this issue. One you hold covers this issue."); under the facts, once, a dim "Owned via <edition's work> (<Format>)" when one of your copies of a collected edition holds the comic; a comic's cover is captioned "Cover from Comic Vine" when Comic Vine is its source. On a collected comic the Editions row also prints "Contents: <line>" ("Nothing yet" when empty), a Comic Vine link when the edition has that source, and an Edit contents button (see the picker below). An unknown id is a 404 inside the app shell.
- Editions and copies (the item page, every type; `src/app/(app)/items/[id]/editions-section.tsx`). The heading reads "<n> in the catalog · you hold <k>" or "· none yours"; with no printing it has no dim line and the body says "None in the catalog yet." Each printing is its format, then its title, publisher, year, pages and ISBN as the catalog holds them. A printing you hold nothing of ends in I own this. Under a printing, one line per copy of yours, oldest first: "Your copy", "<Condition> · since <date>" (either part alone, or none), the note with its line breaks, Edit and Remove.
  - Own a copy (the heading's right) opens one sheet. Format lists the work's printings first ("Paperback · Anchor Books, 2011"), a rule, then the formats the type takes that the catalog lacks: book Paperback, Hardcover, Ebook, Audiobook; comic Floppy and Digital, a collected comic Trade paperback, Hardcover, Omnibus and Digital; film and show DVD, Blu-ray, 4K and Digital. Condition (New, Fine, Good, Fair, Poor), Acquired and a note are optional. Picking a printing posts its edition; picking a format the catalog lacks makes the printing and the copy in one write, with only the format set. Two copies of one printing are two lines. Add it posts once even when clicked twice.
  - If the work has two printings of the picked format the sheet shows the route's 409 line, stays open and writes nothing; Cancel then reads the page again so the printings it named are there. A future Acquired date shows under the field and the sheet stays. Words typed in the note keep the sheet open on Escape and an overlay click; Cancel closes it.
  - I own this posts the printing's edition with no sheet and holds until the page has refreshed. Edit shows Format as text ("A copy's printing doesn't change. Remove it and own the right one."), and sends only the fields you changed, so a save made in another tab is kept. Remove asks "Let go of this copy?", then `"<first line of the note>" goes with it. The printing stays in the catalog.` (just the second sentence with no note); the printing is never removed. Remove or Save on a copy another tab already removed: Remove closes and refreshes, Save shows "No copy by that id." with your words kept.
  - A backup (a short printed inside another comic) has no Own a copy. Its section says "A backup story is owned through the comic it's printed in." and, when you hold the comic, "Yours via <host> (<Format>)"; the host is the comic it is contained in, or, for a backup listed in a held collected edition's contents, that edition's work. A backup has no Owned via line under its facts.
  - The pages that list owned works are `/collection` and `/collection/shopping`, below. The series page's ticks, the shelf row's mark and the ISBN card's box are below too.
- The contents picker (Edit contents, on a collected comic's Editions row): a sheet titled "What does this <format> collect?" listing every comic in the catalog in groups by series text, one-shots and the rest last. The filter matches series text or title and keeps ticks you made under another filter; a line reads "Showing <n> of <total>" and the footer "<n> picked". The edition's current contents are ticked on open. Save contents replaces the edition's contents: a comic already held keeps its place in the printing, new ticks follow in list order, unticked ones go. Cancel writes nothing. The list is the whole catalog's comics, handed to the page when it renders.
- `/items/new`: add an item by hand, for what no provider knows. The fields follow the type.
- `/series/<uuid>`: a Comic Vine series that was imported. A Series pill, then "<years> · <publisher> · <n> issues" (the start year alone while the run has no end year, which is set only when Comic Vine's issue count matches what came in and the last cover date is before this year), the name, "Vol. <n>." and Comic Vine's one-line description when there are any, Publisher and Sources, and an Issues grid in cover-date order: cover, "#<n> · <month year>", the title linking to the item. The count is the catalog's, not Comic Vine's. Add the run to a shelf sits beside the Issues heading (see Add to shelf below). An unknown id is a 404 inside the app shell. The series' own cover is stored and not shown. Under the grid, Collected in lists every edition whose contents hold an issue of this run, each as the title linking to its page and "<Format> · <year> · <contents>", the run's own issues as "#1 to #7" and the rest after ", and"; "Nothing collected yet." when none.
  - Ticks (`issue-tick.tsx`). Under each tile, except a collected edition's, a box "Owned, <title>" with a label: "Owned", "Owned · Floppy", "Owned · 2 floppies". A tile whose form can't take a floppy (`collected`, `backup`) has no box; it prints "Your copy" in accent when you hold it. The boxes are disabled in the server's HTML and enable once the page has hydrated, since a native box clicked earlier shows a tick nothing posted. A tick posts `{ item, format: "floppy" }` to `/api/v1/copies`. An untick first reads `GET /api/v1/copies?item=<issue>`, then deletes the newest floppy in that answer, so the rule runs on the copy as it stands and not as the page last saw it. If that floppy has a condition or a note the box asks first: "Let go of this floppy?", "Its note goes with it." (or "Its condition goes with it." with a condition alone), Remove and Cancel; a date alone doesn't ask. An untick leaves the printing in the catalog. A box takes no second click until its answer and the page's refresh have landed; a refused or lost answer puts the box back, prints "Couldn't change that. Try again." once under the Issues heading and reads the page again before the box takes another click. Cancel is disabled while Remove is out (the shared `ConfirmSheet`); every sheet and confirm holds this way (`useSheetHold`).
  - Holding. The heading's dim line gains " · you hold <h>, <v> of them via a collection": <h> counts the issues you hold as a floppy or through a collected edition, once each, and <v> the ones through one ("· you hold <h>" at no <v>, nothing at no <h>). An issue a held collected edition covers prints "via <that edition's work>" under its box, and "also via …" when its box is ticked. An issue held only as digital prints an empty "Owned" box and counts in <h>. Collected in rows end in "Your copy" or I own this as on the item page, and a closing line under the grid explains the ticks.
- Shelf row's mark (`/shelves/<uuid>`): after the stars and "read twice", a dim "owned" when you hold the work, "via <title>" when a held collected edition covers it (the first by the edition's work title), or "owned · via <title>". Nothing when neither. It reads your copies only, in the shelf's one statement. On the TMNT fixture shelf after a load, 38 rows carry a via mark and none "owned".
- `/journal`: the Journal in the header, after Nook. Every entry of yours across every work, newest first, 50 a page, under a label per day it was written ("1 November 2026", the server's time zone). The lede is "<n> entries across <m> works, newest first." and a second sentence; with none, "Nothing written yet. Open a work, log a read or a watch, and write the first line." A row: the title linking to the item page, a type pill and the work's second line, the read's state ("Reading since 28 October", "Done, 9 March 2019 · ★ 4.5", "Abandoned, 2 May 2020"; the year is left off in the current year; a Done read with a Started date and no Finished prints "Done" alone), the entry's text, its pill when pinned, the time written (24-hour) and Edit and Delete, which are the item page's sheets. When another page follows, "Older entries" at the foot links to `/journal?before=<written_at>,<entry id>` (the keyset: entries on one instant never repeat or vanish between pages); there is no link back but the header, and a `before` page with nothing under it says "Nothing older than this." with a link to the newest. A `before` that is not a real UTC timestamp with microseconds and a uuid is a 404 inside the app shell, never a 500. Long unbroken text wraps inside the row. Only your own entries are listed.
- `/collection`: the Collection in the header, after Journal. "Your collection", then "<n> copies of <m> works, newest first." and, when your copies cover other works, " <k> more works are yours through what they collect." (on a fresh fixture load: "5 copies of 5 works, newest first. 38 more works are yours through what they collect."). With no copy the lede is "Nothing held yet. Own a copy from a work's page, or tick a run on its series page." The outline button at the right reads "Shopping · <s> to find" (314 on a fresh load) and links to Shopping.
  - The chip rail (All, Books, Comics, Films, TV) is absent with no copies. A chip is a link to `/collection?type=book|comic|film|tv`; it filters the rows and leaves the lede whole, a chip with no rows says "Nothing here yet.", and picking one drops any `before`.
  - A row is one copy: cover, the work's title linking to its page, a type pill, then a line of the printing: the format, "covers <n> issues" when the printing has contents, then "<publisher> · <year>" or, with no publisher, the work's own second line ("Hardcover · covers 8 issues", "Paperback · Anchor Books · 2011", "Blu-ray · 1976"). A third line, "<condition> · since <date> · <note>" with any part left out, shows only when the copy has one, and clamps at two lines. Edit and Remove are the item page's sheets, mounted on the row. Cancel on either is disabled and Escape ignored while a write is out; after one was tried, closing reads the page again.
  - 50 a page, newest first, by keyset: "Older copies" at the foot links to `?before=<created_at>,<copy id>` (the Journal's cursor, one parser: `src/lib/journal/cursor.ts`, whose field is now `at`), keeps `type`, and copies written at one instant page by id. A `before` that doesn't parse, a `type` off the list and a repeated `type` are a 404 inside the app shell. Past the end the page says "Nothing older than this." with "Back to the newest".
  - Every read filters on the caller: another person's copies and shelves move none of the rows, `n`, `m`, `k` or `s`. `s` is `toFind` in `src/lib/collection/owned.ts`, the same fragment Shopping counts with, so the button and Shopping's lede can't disagree.
- `/collection/shopping`: Shopping, the button's page. "Shopping", a Back to your collection button, and the lede "<s> works on your shelves you don't hold a copy of, by shelf. A work on two shelves is listed once, under the first." (no shelves: "No shelves yet, so nothing to find."; shelves and none to find: "Nothing to find."). Nothing is stored and it does not page: every row is on the page (314 rows on a fresh load; the page was 936,101 bytes on a production build).
  - One block per shelf in the nook's order (`NOOK_ORDER` in `nook-page.ts`, shared), the name linking to the shelf and "<a> of <b> to find" beside it, then the shelf's rows, the unsectioned first and then each section by position under its name, a section with no row to find printing no name. A row is the Collection row's cover, title, type pill and the work's second line, "Also on <later shelves>" when a later shelf holds the work too, and I own this at the right.
  - A row to find is a work neither held nor owned via a collection, and not a backup. "<a>" counts that for this shelf alone, so a work listed under an earlier shelf still counts on a later one and the shelves' counts can add up to more than the lede's total. A shelf whose rows all sit under an earlier shelf prints no rows and "Listed under <first shelf>.". A shelf with works and nothing to find, backups held through their host included, reads "Everything here is yours."; a shelf with none reads "Nothing on this shelf yet."
  - Backups are left out of the rows and counted: "<n> backups left out: you'd buy what they're printed in." ("1 backup left out: you'd buy what it's printed in."), under the rows. On a fresh load that is 47 on the TMNT shelf; the shelves read "242 of 326 to find", "61 of 61 to find" and "11 of 11 to find".
  - I own this opens the Own a copy sheet for that work, with the work's printings first in Format (a film's row offers DVD, Blu-ray, 4K and Digital). Add it posts once; the row leaves the list on save and the lede follows, with no reload. Cancel reads the page again only after a post was tried. Escape or Cancel returns the keyboard to the row's I own this. Each row carries every printing of its work for the sheet, which is most of the page's weight (a Deferral in the plan: the trigger is a warm hit past 1 s on a production build).
- `/nook`: "Your nook" and a line of totals ("3 shelves · 398 works on them"; with a work done, "· <n> done"). With no shelves the line is "No shelves yet. Make one and it stops being quiet." and there are no cards. Each shelf is a card linking to `/shelves/<uuid>`: its name, its counts ("326 works · 14 sections · 38 owned", "· from Letterboxd" when the shelf has a source link; "<n> owned" counts the shelf's works you hold or hold through a collected edition, each once, and is left out at 0; on the TMNT fixture shelf after a load it is 38, on the other two 0), the description clamped to two lines, and a strip of the first five covers (a dashed box where there is none) with "+<n>" for the rest. Cards run newest change first (`updated_at`, then `created_at`, then name), two across at desktop width. New shelf opens a sheet with a name and a description; Make shelf lands on the new shelf's page. A blank name shows "Give the shelf a name." and stays on the sheet.
- `/shelves/<uuid>`: a shelf you own. A Shelf pill and its counts, the name, the description as written (blank lines kept), a row of buttons, then the works. ## CI

Every PR into `dev` or `main`, and every push to `dev`, runs workflow `CI` (`.github/workflows/ci.yml`). It has six jobs, named as their npm scripts: `lint`, `typecheck`, `test`, `db:check`, `test:db`, `test:e2e`. `test:db` and `test:e2e` each start their own Supabase stack in the runner, including Storage for the `covers` bucket. `test:e2e` builds the app and runs it with `next start` on Chromium only. No secrets are used: `.env.example` is copied to `.env.local`, and `SUPABASE_SECRET_KEY` is filled from the key that stack prints. CI holds no TMDB or Comic Vine key: the tests run on the stubs, and the one test that calls each real keyed provider skips without its key. Open Library needs none; all three stubs start in Playwright's global setup.

`npm run check` runs the same six gates locally.

When a check is red:

- Open the job's log. The failing gate's own output is there.
- A red `test:e2e` also uploads a `playwright-report` artifact, with traces.
- A red `db:check` prints the SQL a migration would need, or drizzle-kit's error. A rename needs answering in a terminal: run `npm run db:generate -- --name=<what_changed>` and answer it.
- A job that fails while pulling Supabase images with `toomanyrequests` hit a registry rate limit, not your change. Re-run the job.

Workflow `Nightly` runs the whole Playwright suite on `dev` at 04:17 UTC, one job per browser (Chromium, Firefox, WebKit). Its browser install step is capped at 10 minutes. Start it by hand from the Actions tab or with `gh workflow run nightly.yml --ref dev`. It does not run on PRs.

Workflow `Build` (`.github/workflows/build.yml`) runs on every PR into `dev` or `main`, on a push of a `v*` tag and when a Release is published. It is separate from `CI`, whose six jobs it doesn't touch. Job `android` (`ubuntu-24.04`) signs the apk with the key in the repo's secrets and job `windows` (`windows-2025`) builds the NSIS installer; each has a 30-minute cap, and the first run took 4 m 41 s and 5 m 11 s cold. A PR from a fork has no secrets, so `android` fails there in words. A tag's own run finds no Release (it is made after the tag), so the `release` run attaches the files. A newer push doesn't cancel a run in progress. Workflow `Probe` (`probe.yml`) builds the probe's two debug apks and the generated Android project, and runs only when the probe's own files change. See Install on a phone.

Tests that sign in should import `test` and `expect` from `tests/e2e/harness/signed-in`. The session is on `page` and `page.request`; Playwright's built-in `request` is signed out.

## Fixtures

`supabase/seed` holds the acceptance data every later chapter is checked against. Today that is L's Stephen King watch list from Letterboxd, built into two files from the one raw CSV: `king-films.json` (61 films, one shelf) and `king-books.json` (27 book items, 78 relations, one shelf, one gap); and the Mirage tab of L's TMNT sheet, `tmnt-mirage.json` (366 comics, 47 relations, 5 editions, 5 copies, 26 occurrences, one shelf of 14 sections, 9 gaps).

- `supabase/seed/raw/<source>/`: exports exactly as their source wrote them. Never edit one by hand. Each has a row in `supabase/seed/raw/README.md`.
- `supabase/seed/fixtures/<name>.json`: generated, committed, never edited. `npm run fixtures:build` writes it. A second run leaves `git status` clean.
- `src/fixtures/shape.ts`: the Zod shape of a fixture file. Item ids are `<source>:<key>`; the King films are `letterboxd:<boxd key>`. An item with no provider is `manual:<slug>-<year>` with `providers: {}` (`manual:salems-lot-1975`; apostrophes and accents are dropped from the slug).

Items are a `film`, a `book` or a `comic`. A book has an `author` and a `form`: `novel`, `novella`, `collection`, `story` or `series`. A short story is a book with form `story`; Night Shift is the `collection` its 16 stories are in. The King notes name the works; `scripts/fixtures/king-works.mjs` reads them out of the films' `source_note`s.

A comic has a `form`: `issue`, `one-shot`, `backup` (a short printed inside another comic), `collected` (a trade or hardcover as a work) or `anthology` (a host the run doesn't list as its own). It also has `series`, `series_kind` (`ongoing`, `micro-series`, `mini-series`, `crossover`, `tie-in`, `minor`), `number`, an optional `month`, and `source_date`, the sheet's date cell verbatim. `year` can be null on a comic and nowhere else; a row or anthology with no year is a `gaps` line, while an Ultimate Collection's year is its edition's, which the sheet doesn't hold. The sheet's columns mean different things in different sections, so `scripts/fixtures/mirage-tab.mjs` has one rule per section header. Its ids are `manual:tmnt-mirage-v1-7` for a numbered row, `manual:tmnt-mirage-<section>-<title>` otherwise, `manual:tmnt-mirage-host-<cell>` for an anthology and `manual:tmnt-ultimate-collection-<n>`. The two `Savage Dragon #2` rows are two items; the later id ends in `-r212`, its record number.

A file may also carry:

- `relations`: `{ type, from, to }`, `type` being `adaptation-of` (from the adaptation to its source) or `contained-in` (from the part to the whole). Either end may be an item in another file: `king-books.json` holds the relations, and its `adaptation-of` ones start in `king-films.json`.
- `gaps`: `{ item, reason }`, an item the raw file gave nothing to build from. Recorded, not filled in, and not a relation. Today: The Long Walk (`letterboxd:mic8`), "no source note", and the nine undated Supplemental/Crossover rows, "no readable year".

- `editions`: `{ id, item, format, contents }`. `id` is `edition:<key>`, `item` is the work it prints (in the same file), `format` is `floppy`, `tpb`, `hardcover` or `omnibus`, `contents` the items it collects. An edition id never passes as an item id.
- `copies`: `{ edition, note }`, a copy of an edition.
- `occurrences`: `{ item, status }`, `status` being `done`.

All of these read as empty when absent. A shelf has `entries` or `sections` (`{ name, entries }`, positions restarting in each in the file; the loader numbers them 1 to n across the whole shelf), never both; its `url` is optional, and the Mirage shelf has none because the sheet is private. A work has one year, the one its note gives; a second year for the same title stops the build.

Owned via: an issue listed in an edition's `contents` is owned through the copy of that edition. That is never written as `contained-in`, which is for a backup inside its host. Read is an occurrence and is never derived from a copy.

`npm test` goes red when a fixture disagrees with the shape or with a fresh build of its raw file (`tests/unit/fixtures.test.ts`). The same file checks every fixture together: no id is defined in two files, and every relation endpoint, shelf entry (flat or in a section) and gap names an item in some file, every edition content, copy and occurrence resolves, and no edition id is defined twice. The shape alone can't see across files. The fresh build goes to `node_modules/.cache/fixtures`; no test writes to the repo.

The build stops, naming the raw file and record, when an export changed shape: different headers, a non-empty `Tags`, a URL that isn't `https://boxd.it/<key>`, a Year or Position that isn't a whole number, a film listed twice with different data, or a list with no films. The Mirage build stops, naming the fixture, raw file and record, on a section header it has no rule for (or one repeated in a volume), a row its section's rule can't read, an `Owned` and `Format` that disagree, or an id that repeats outside Supplemental/Crossover. A date with no year does not stop it; that is a gap. The books build also stops, naming the fixture, raw file, record and note line, on a note line it can't read, a story with no collection, two lines that disagree about one work or its year, a line repeated within one note, or a shelf work no first note line names. No fixture is written until every fixture has built, and two `SOURCES` lines with one `out` stop the build. It never drops a row quietly. A hand-edited raw file shows up as a red byte compare, not as a fix.

Adding a raw file: put it under `supabase/seed/raw/<source>/`, add its row to `supabase/seed/raw/README.md`, add a `SOURCES` line in `scripts/fixtures-build.mjs` per fixture (a raw file may feed more than one; builders live in `scripts/fixtures/<name>.mjs`, and a new source needs its own; each `out` must be new), run `npm run fixtures:build`, and commit the raw file and its JSON together. From a Google Sheet, export one tab per file (File > Download > Comma-separated values) under `google-sheets/`; a new tab needs its own section rules. The CSV reader is `scripts/fixtures/csv.mjs`, written in-repo; no package was added.

## Data model

`src/db/schema.ts` holds 22 tables in `public`, in two halves. The item page reads the catalog, the signed-in user's shelf entries and their `occurrences` with each read's `journal_entries`; the nook and the shelf page read shelves, sections and entries; the item page, the series page and the shelf page read the signed-in user's `copies` (the shelf page as a held flag and a via title per row), and the ISBN card asks `GET /api/v1/copies?item=` for whether you hold a printing.

- The catalog, shared by every user, no `visibility`: `items` (a `film`, `tv`, `book` or `comic`; `form` is null for films and shows and required for books and comics; `summary` and `cover_path` are shared by every type), `item_films` (runtime, original title), `item_tv` (seasons, episodes, original title, first and last aired, ended), `item_books`, `item_comics`, `item_sources`, `item_relations`, `editions`, `edition_sources`, `edition_contents`, `franchises`, `franchise_sources`, `item_franchises`, `series`, `series_sources`. A `series` is a comic run (name, volume, years, publisher, kind, summary, cover) and `item_comics.series_id` points at it, nullable, restrict on delete; the `series` text column stays. `POST /api/v1/series/import` writes a `series` row, its `series_sources` row, and every issue as a comic with `series_id` set (see `docs/API.md`). A Comic Vine key is `volume/<id>` on `series_sources`. An item's identity is its `item_sources` row, `(source, key)`: the fixtures' `letterboxd:20ZQ` is source `letterboxd`, key `20ZQ`, and `manual` is a source like any other. A TMDB key carries the kind, `movie/603` or `tv/1396`, because the ids collide; an item added by hand has its own uuid as its `manual` key and its `created_by` set (loader rows have it null). Open Library keys are `works/OL…W` on an item and `books/OL…M` on an edition. An ISBN is an `edition_sources` row with source `isbn` and the ISBN-13 as its key, so it is unique across the catalog. `editions` carries a nullable `publisher` and `pages` (above 0); the loader leaves both null. Dates are `released_on` plus `released_precision` (`day`, `month`, `year`), both null or both set.
- A person's content: `shelves`, `shelf_sections`, `shelf_entries`, `occurrences` (a read or watch, with half-step `stars`), `journal_entries`, `copies`. Everything here points at the catalog and never the other way round.
- `profiles` is an account table: no `visibility`, no `updated_at`.

Visibility is `private`, `unlisted` or `public`, default `private`, on `shelves`, `shelf_entries`, `occurrences`, `journal_entries` and `copies`. `shelf_sections` has none; the shelf's is the section's. `owner` is on `shelves`, `occurrences` and `copies` only: the rest reach their owner through their parent. Nothing enforces that a child is no more visible than its parent yet.

Deletes: removing a `profiles` row removes everything that person owns and leaves the catalog alone. A catalog row can't be deleted while a shelf entry or occurrence points at its item, or a copy at its edition. Deleting a shelf deletes its sections and entries. Deleting a shelf section row deletes its entries too, in the database; the section route moves them above the first section first, so through the API no work goes with a section.

Every enumeration is `text` with a check constraint, not a Postgres enum. Every table but `profiles` has `updated_at`, kept by the trigger `<table>_updated_at`.

A copy's `condition` is `new`, `fine`, `good`, `fair`, `poor` or null (check `copies_condition`); `acquired_on` and `note` are the other optional fields. A copy of a printing the catalog lacked makes an `editions` row with only `item` and `format` set. The copy routes are in `docs/API.md`.

Owned via: a work is owned when a copy's edition holds it, and a backup when the comic it is contained in (`item_relations`, kind `contained-in`) is held or held via, one hop. There is no column for it; it is a query over `copies`, `editions`, `edition_contents`, `item_relations` and `items`, in `src/lib/collection/owned.ts`, the one place that reads it. Read is an `occurrences` row and is never derived from a copy. A person has at most one `in_progress` occurrence per work: the partial unique index `occurrences_one_open` on `(owner, item)`.

```sh
docker exec supabase_db_fluxnook psql -U postgres -tAc "select i.title || ' | owned via ' || w.title from copies c join editions e on e.id = c.edition join items w on w.id = e.item join edition_contents ec on ec.edition = e.id join items i on i.id = ec.item order by w.title, ec.position"
```

After the fixtures are loaded this returns 37 rows.

The loader, `npm run fixtures:load -- --user <email>`, reads every file under `supabase/seed/fixtures`, checks each against `src/fixtures/shape.ts`, and writes in one transaction: the catalog first, then the user's shelves, sections, entries, copies and occurrences. After a reset and one load the counts are 454 `items`, 454 `item_sources`, 125 `item_relations`, 5 `editions`, 37 `edition_contents`, and for the user 3 `shelves`, 14 `shelf_sections`, 398 `shelf_entries`, 26 `occurrences`, 5 `copies`. `gaps` are printed and not loaded.

- The address is matched without regard to case, and must already be signed in. With no auth user or no `profiles` row it exits 1 and says which.
- The catalog is upserted on its source key, so a second run adds no catalog row. It does not refresh a row's `item_sources.url`, and does not remove a relation or content that has left a fixture.
- Content loads only into a user who has none. A second plain run exits 1 with `already has ... pass --replace` and writes nothing. `--replace` deletes that user's shelves, occurrences and copies, with their sections, entries and journal entries, then loads again. The log names the email before it deletes.
- Two loads for one user at once: the second waits, then refuses.
- `npx supabase db reset` removes all of it. Sign in again, then load.

Raw SQL by hand: `docker exec supabase_db_fluxnook psql -U postgres`, as above. Studio is at http://127.0.0.1:54323.
