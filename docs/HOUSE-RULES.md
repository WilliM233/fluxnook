# Fluxnook House Rules

How a chapter gets built. One copy lives here; the Project's synced `docs/` copy is a read-only mirror. When a rule changes, edit this file and add a History line. The Afterword is the only process that may change this file, and it must. A refinement pass taken between a merge and the next chapter's spec lands as an addendum to the last Afterword, in the next chapter's spec commit, with its own History line.

## Vocabulary

| Word | Means |
|---|---|
| Volume | A milestone. One GitHub milestone, one `dev` to `main` merge, one tag |
| Chapter | One Roadmap line, one design talk, one spec, one chapter issue, one Afterword. Bound from one or more Signatures |
| Signature | The unit that is built: one issue, one branch, one PR, one squash commit, one Browse. A chapter the Cartographer cuts as one has one Signature, numbered `.1` |
| Cut | The Cartographer's division of a chapter into Signatures, in Run 1: what each delivers, which acceptance lines it owns, in what order |
| Run | One Claude Code session. Run 1 of a chapter is the map and the cut; every Signature after it is its own run |
| Plan | The chapter's file at `docs/plans/<vol>.<n>-<slug>.md`, sections 0 to 2 and the cut; each Signature's file at `docs/plans/<vol>.<n>.<s>-<slug>.md`, sections 3 to 5 |
| Rummage | The Raccoon's attack list; every line becomes a test that is seen red, then green |
| Browse | L's hands-on walk through the chapter as a user, before sign-off |
| Afterword | The three-line retro on the issue before it closes |
| Stop-for-L | A design question the Cartographer found that only L can answer |

## Seats

| Seat | Who | Model | Does one thing |
|---|---|---|---|
| Nookkeeper | Product owner; the Cowork project session | Fable | Spec and feasibility, plan review, PR review, sign-off, runs the Afterword. Cannot write to GitHub |
| Cartographer | Architect subagent (`.claude/agents/cartographer.md`) | Fable | Census of what exists and the cut in Run 1; a Signature's steps and Stop-for-L list in its run. Never writes app code, never records a provider |
| Binder | Claude Code main session (`CLAUDE.md`) | Opus | Opens the chapter and Signature issues, builds a Signature step by step, spawns the other agents one at a time, opens the PR. Never merges or closes |
| Raccoon | QA subagent, fresh context (`.claude/agents/raccoon.md`) | Opus; Fable when the spec's QA model line says so | Diff vs plan, the Rummage, the failing tests. Never fixes what it finds |
| Scribe | Docs subagent, fresh context (`.claude/agents/scribe.md`) | Sonnet | README, docs, the release note. Reads the diff and the plan, never the Binder's summary |
| L | The human | | Opens the chapter branch, design calls, Stop-for-L answers, the Browse, PR review, CI check, the merge. First commit and last click |

The model is set in each agent file's frontmatter. The spec's **QA model** line is Fable when the chapter opens a door: auth, visibility, migrations on content tables, import or export, anything that can lose or expose a person's data. Otherwise Opus.

Subagents run one at a time, never concurrently. Five seats is the ceiling until an Afterword says a sixth is being skipped by hand.

## A chapter's life

From Ch 1.4 a chapter is bound from Signatures (Ch 1.3 Afterword addendum: 22 commits and 96 files in one PR, and a Browse too long to run clean). Steps 0 and 1 happen once per chapter; Run 1 maps and cuts it; steps 2 to 8 happen once per Signature, each in a fresh session on its own branch off `dev`; step 9 happens once, after the last Signature merges. Signatures run one after another, never side by side: each builds on the last one's merged `dev`.

0. **Pick.** The next chapter in the open Volume on the Roadmap. Design talk between L and the Nookkeeper; every call lands in the Roadmap's Calls list with its reason. A chapter that brings a screen gets its design made in the Nookkeeper's seat during the design talk, drawn on the Deep Field design system (`docs/designs/deep-field/`, the artifact linked there) so no screen invents a token; section 0 links it, so the team builds to an expectation set up front. A provider chapter probes the provider's API with a key before the screens are drawn, not after: what a list call serves decides what a page can show (Ch 1.4: Creators was drawn, then found to be a detail call per issue, and deferred). L opens the branch before the Nookkeeper writes the plan: `git checkout dev && git pull && git checkout -b chapter/<vol>.<n>-<slug>`.
1. **Spec.** Nookkeeper writes Plan sections 0 and 1 (spec, acceptance lines, feasibility read against the repo, Hands line, Browse line) into `docs/plans/` on the chapter branch, in L's checkout; the plan and the Roadmap edits are the branch's first commit, pushed by L: `git add docs/ROADMAP.md docs/HOUSE-RULES.md docs/plans/<vol>.<n>-<slug>.md docs/designs/ supabase/seed/raw/ && git commit -m "docs: ch <vol>.<n> spec" && git push -u origin chapter/<vol>.<n>-<slug>`. Any raw input the chapter needs (an export, a sheet) lands under `supabase/seed/raw/<source>/` in that same commit, so the census sees real data. A chapter with screens carries their exports in the same commit: PNGs under `docs/designs/<vol>.<n>/` with a README naming each, and the design system's tokens as text under `docs/designs/deep-field/`, since the team can't open the private canvas (Ch 1.2). The spec commit starts from a clean `git status`, and so does the Binder's session: anything else is restored or explained before a line is written (two stray edits appeared between Ch 1.2 and 1.3, source unknown). Every state the Browse line names is produced by an earlier line of the same Browse from a fresh reset (Ch 1.2's Browse named a Carrie no fresh load could show). The Hands line lists L's prerequisites, each with the command that checks it, and the Binder's step 1 runs those checks before anything else. Command blocks for L are Git Bash (MINGW64), never PowerShell. A block that pipes into Node writes `node.exe`: Git Bash's `node` is an alias for `winpty node.exe`, aliases don't survive a pasted block, and every piped line fails without it (Ch 1.2). The repo copy of every standing doc is the one that counts; the project's copies are read-only mirrors synced from `dev`. The Binder opens the chapter issue from the plan at its next session start: body is section 0 plus a link to the plan, milestone is the Volume, label `chapter`; then writes the number into the plan header. No agent is spawned for a chapter without an open issue.
1b. **Map and cut (Run 1).** A fresh Binder session, no code. The Binder spawns the Cartographer once for section 2 (the census) and the cut: the Signatures in order, each with a name, a slug, the acceptance lines it owns, what it leaves to the next, and which one carries the chapter's end-to-end Browse (the last, unless the cut says why not). One Signature is a valid cut; the Cartographer measures (new tables, new screens, provider calls, acceptance lines), it doesn't fill a quota. Census corrections to section 0 are carried as step 2 says. The Nookkeeper reviews the cut against the spec, Pilot or not: every acceptance line owned exactly once, no Signature depending on a later one, the exit Browse placed. `Approved` or changes. The Binder opens one issue per Signature (body: its slice of section 0 and the cut's line, linked to the chapter issue, label `signature`, milestone the Volume), writes the numbers into the chapter plan, commits `docs: ch <vol>.<n> census and cut`, and stops. The chapter branch already holds the spec and the cut, so the first Signature is built on it; from the second on, L opens `git checkout dev && git pull && git checkout -b signature/<vol>.<n>.<s>-<slug>` once the one before it has merged.
2. **Map.** In a Signature's run: the Binder spawns the Cartographer on the Signature issue. In a Signature that brings a provider call, the Binder records the provider's answers first, with the recorder, before the Cartographer writes a step: a plan written before its recordings moves at build (Ch 1.4.1: three facts moved at step 5; 1.4.2 recorded first and every fact held). Cartographer writes the Signature's plan file, section 3 (steps with observables) and the Stop-for-L list, reading the chapter plan's sections 0 to 2 and the cut, and re-reading the census where `dev` has moved since Run 1 (a census delta, not a second census). L answers Stop-for-L; Nookkeeper reviews the plan against the spec: every call kept, no scope added, observables match acceptance lines. Reply is `Approved` or a list of changes tied to spec lines. The Cartographer is re-engaged only to restructure. When the Pilot rule has trimmed this gate, the Binder builds on sight and the Nookkeeper's read of the plan goes to the Afterword. Either way, the census's corrections to section 0 (a number, a name, a state the Browse can't produce) are carried into section 0 and the issue body by the Binder in the census commit, each marked `(census)`, so the Browse is written against the measured plan; the Nookkeeper verifies them at review rather than making them (Ch 1.3: under the Pilot nobody read section 0 against the census until review, and the Browse ran on a stale year).
3. **Build.** Binder works the steps on the Signature's branch off `dev` (the chapter branch for the first Signature). Each step ends at its observable. A step's Does, Touches, Observable and Tests are the contract; its How is advisory, and the Binder may improve on it without a deviation line when the observable is unchanged. The Binder stops only for a Stop-for-L, a deviation that needs a call, or a red it can't fix inside the plan; otherwise it runs the steps through to the handoff, and the Nookkeeper reviews section 5, not each step. The PR may open as a draft as soon as a workflow needs an event to run on. A side find is a Deferrals line on the plan, never a step.
4. **Rummage.** Binder spawns the Raccoon with the diff and the plan. Raccoon writes section 4: findings (blocking, should, note) and the Rummage. Blocking findings are fixed in the chapter. Every Rummage line becomes a test; Binder watches each fail before it passes.
5. **Scribe.** Binder spawns the Scribe with the diff and the plan. Scribe updates README and docs that the chapter changed, and drafts `docs/releases/<vol>.<n>.md`. Accuracy over verbosity: if a sentence can't be checked against the diff, it goes.
6. **PR.** Binder marks the PR into `dev` ready with the template filled, `Closes #<issue>` (the Afterword is the branch's last commit, so closing on merge is right; a closing keyword is also what links the PR in the issue's Development panel). CI must be green. Whenever section 0 changes, the Binder updates the issue body in the same commit; the issue is the spec. The Binder comments on the issue at each seat handoff (plan approved, Rummage done, PR ready) so the issue reads as the chapter's log. The PR's Browse section carries section 5's Browse block: runnable Git Bash commands with the expected output under each, written by the Binder from section 0's Browse line. Anything in it that isn't a command for the terminal the block runs in (start the dev server or a stub in another terminal, click in the browser, stop a process) ends the fenced block and stands as its own numbered line in prose, never a `#` comment inside a block; and the first command after such a line checks the state it set up (`curl -s -o /dev/null -w '%{http_code}' http://localhost:3000/` expecting `200` while the dev server should be up, `000` once it should be down), so a missed step fails on its own line with a number instead of three lines later with a stack trace (Ch 1.3: the dev server start and stop were comments, and `npm run check` reused the live-provider server). A Browse that begins with `db reset` signs in again before it loads fixtures: a reset drops auth users too. A count in the block is one the walk controls, measured on the walk rather than on a fresh load when the walk has written before it is read (Ch 1.4.3: 83 on a fresh load, 84 in the walk); a count the walk doesn't control is asserted zero, not counted (Ch 1.4.1: a log line count moved when a browser tab hit the route); a number a live provider decides is written "stub n, live measured at the Browse" (Ch 1.4.2: 143 covers on the stub, 142 live, one over the cap); and a step that saves a file for a later restore checks the save on its own line (`cp … && cmp … && echo saved`), since a skipped save only shows at the restore (Ch 1.4.1). At the Afterword commit the Binder fills the PR's Review line from the plan's History.
7. **Browse.** From Ch 1.5, section 5's commands are a script the Binder writes with the handoff, `scripts/browse/<vol>.<n>.<s>.sh` (Git Bash; the expected output of each check inside it), which prints every check as expected, actual and pass or fail, stops at the first prose step and resumes after it, and writes `test-results/browse-<vol>.<n>.<s>.txt`; L runs the script, walks the prose steps by hand (the clicks, and how the thing feels to use), and pastes the report and what differed under the Browse in the PR; the Nookkeeper verifies the report against section 5. The commands were matching line for line by Ch 1.4 while the clicks were finding things (the import sheet's select left on No doubled a run in one click), so L's attention goes to the clicks (L, Ch 1.4.3 Browse). Up to Ch 1.4: L runs section 5's Browse block in Git Bash and pastes what differed, if anything, under it in the PR. Anything that breaks in the Browse is a blocking finding and goes back to step 3. A Signature's Browse covers what it delivered; the Signature that carries the chapter's exit walks the chapter end to end.
8. **Review and sign-off.** Nookkeeper and L both read the PR. Nookkeeper checks the handoff against the plan, not memory, and cites House Rules from this file as it stands, never from memory (Ch 1.1 D1). A count in section 0 or 1 is measured from the file after the rules the section declares (Ch 0.6); a section 0 correction is verified on disk before it goes to the Binder. A census correction the Binder carried at step 2 is verified here; one it missed is the Nookkeeper's to name and the Binder's to carry before the Afterword commit, issue body in the same commit; an issue that contradicts its own fixture is not closed. Then: every step landed or has a named deviation, every Rummage line seen red then green, every Defer has a trigger, docs match the diff. Reply is `Signed off`, `Signed off with notes` (notes filed to Deferrals or Roadmap now), or `Not yet` with gaps in step order.
9. **Afterword.** Once per chapter, after its last Signature merges: three lines on the chapter issue, mirrored in that last PR's Afterword section, drawn from one retro line the Binder leaves on each Signature PR at its handoff: what worked, what didn't, what changes. A process change edits this file; a knowledge change edits a skill in `.claude/skills/`; stale standing docs the chapter's seats couldn't touch are fixed here too. Those edits are the last commit on the chapter branch, `docs: ch <vol>.<n> afterword`, so they ride the PR. If no file changed, the Afterword isn't done.
10. **Merge.** L checks CI, squash-merges (subject is the Signature's conventional-commit line, 60 characters or fewer), pulls `dev`, tags the squash commit `v0.<vol>.0-ch.<n>.<s>`. The Signature issue closes itself; the chapter issue is closed by L after the Afterword, since no PR carries it.

## Git

- `main` is the released product. `dev` is the open Volume. Neither takes a direct push.
- Branches: `chapter/<vol>.<n>-<slug>` carries the spec, Run 1 and the first Signature; `signature/<vol>.<n>.<s>-<slug>` each Signature after it. All off `dev`, squash-merged by PR.
- Volume close: PR `dev` to `main`, merge commit, tag `v0.<vol>.0`. Volume 0 is `v0.0.0`, alpha `v0.1.0`, beta `v0.2.0`, 1.0 `v1.0.0`.
- Signature merge into `dev`: tag `v0.<vol>.0-ch.<n>.<s>` on the squash commit, so every merge has a version (chapters up to 1.3 are `v0.<vol>.0-ch.<n>`). Pre-release identifiers keep them ordered before the Volume close.
- Hotfix on `main`: patch bump, `v0.<vol>.1`, `v0.<vol>.2`, then merged back to `dev`.
- A merge into `main` is a release. A Volume tag and a hotfix tag each get a GitHub Release whose notes are the PR body. Chapter tags are pre-releases and get none.
- `package.json` version is the current tag; the Scribe bumps it in the chapter that earns it.
- A correction to a migration this branch created, which nothing past the branch has applied, is folded into that migration (regenerate; header and Down move with it), not appended. Appending is for a migration that has reached dev.
- A `test` branch is added only when a test environment exists that previews don't cover. Until then, Vercel preview per PR is the test environment.
- Conventional commits: `feat`, `fix`, `chore`, `docs`, `ci`, `test`, `refactor`. Scope is the area (`shelves`, `providers/tmdb`, `schema`). Body says why, not what.
- No commit without a Signature. Hotfixes are a one-step chapter of one Signature with a Browse line.
- No secret-shaped value is committed, a tool's local default included. `.env.example` carries the slot empty, and CI fills it from the tool that owns it (`npx supabase status -o env` for the Supabase secret key). GitHub push protection refused the local default when a plan quoted it (Ch 1.2 D1).
- A chapter with no PR (Chapter 0.1 was one) is tagged by hand on its commit.
- The Nookkeeper's seat cannot write to GitHub. The Binder opens issues and PRs; L merges PRs and closes issues; anything else (labels, milestones, protection) is a command block the Nookkeeper hands L. The Nookkeeper never reports a GitHub write as done until L or the Binder confirms it.

## Tests and CI

- Every PR: Biome, typecheck, Vitest, Drizzle migration check, Playwright smoke suite. Full Playwright nightly on `dev`.
- Supabase local runs in CI; e2e hits a real Postgres, never a mock.
- A Rummage test that can't be made to fail first is a finding against the test, not a pass.
- Fixtures are the acceptance data: the King path and the TMNT Mirage tab live in `supabase/seed` as data files from Volume 0 Chapters 4 to 6 (one chapter per media type) and every later chapter is accepted against them.

## Plan file

`docs/plans/TEMPLATE.md` is the chapter's shape: 0 Spec · 1 Feasibility · 2 Census · the Cut. `docs/plans/TEMPLATE-signature.md` is a Signature's: a header pointing at the chapter plan, then 3 Steps · 4 Rummage and findings · 5 Handoff. Deferrals and History at the bottom of each. The file is the record; chat is not.

## Pilot rule

At each Signature's sign-off the Nookkeeper answers two questions in one line each, filed on this file's History at the chapter's Afterword: did the Cartographer's plan need corrections? Did the Raccoon find something the Binder missed? Two clean Signatures in a row on a question trims that gate (the Cartographer's plan is approved on sight; the Raccoon runs only its Rummage). One hit restores it. This is what keeps the ceremony proportional to the project.

## Whimsy

Names are the vocabulary above and nothing is renamed to sound serious. Release notes are written for the people who'll use the nook, in plain words. The Raccoon's findings may be a little smug. The Scribe's may not.
