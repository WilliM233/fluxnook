# Fluxnook Roadmap

Standing doc for the product-owner seat; the repo copy mirrors the project copy. Volumes are milestones, chapters are runs the dev team lands one at a time. A chapter opens only when its plan is written and approved. Edit this file when a call changes; add a History line.


## What Fluxnook is

A media nook: collect films, TV, books, comics, games (more later) in one place, organize them into shelves, log each read or watch with a quick star rating and a journal entry, and track the physical library alongside. Letterboxd plus Goodreads plus the collector's spreadsheet, with a journal in place of the critic's review. It lives on your phone and PC first (Volume 2), with nothing to host; the hosted nook with the social layer comes after (Volume 3), and everything carries over. Sharing comes after the single-player product is something you would miss.

## Principles

- Complete product at every milestone, then enhance. No goliath out of the gate.
- Data model before stack. The relational design is the consequential decision; everything else is replaceable.
- Private by default. Visibility is a column from the first migration; the social layer is built on it later, never bolted on.
- Journal, not review. Entries are many, dated, anchored to a specific read or watch. Stars are a quick note of how it felt, not a verdict.
- Collection is first-class. Owning a copy is a different fact from having read the item.
- Providers do the typing. Manual entry exists as the fallback, never the main path.
- The app helps curate, the user controls the list. Suggestions are offered, never forced.
- Your nook is on your device. The hosted nook is a copy you choose to make, and the same tables both places, so moving is an export and an import, never a translation.

## Stack (lock exact versions in Volume 0)

- Next.js + TypeScript, single app, no monorepo until a second client exists
- API surface: Zod-validated route handlers under /api/v1; no server actions for mutations, so a native client is a drop-in later
- Postgres on Supabase; Supabase CLI for local (Docker), Supabase cloud for hosting. Same shape both places
- Drizzle ORM (plain SQL migrations, readable in review). RLS off; authorization lives in the API layer
- Supabase Auth (email + magic link; OAuth is 1.0+). Custom auth ruled out
- Supabase Storage for cover cache and photos of owned copies
- Tailwind + shadcn/ui, Vitest + Playwright, Biome
- Device build (Volume 2): the same app in a shell, Tauri 2 or Capacitor, picked at the Ch 2.1 census (replaces "PWA then TWA", 2026-11-05); PGlite (Postgres in WASM) on the device with the same migrations, one local profile, no sign-in; a sideloaded signed apk and a Windows build out of CI on every PR and tag. The Play Store is Volume 3
- Hosting: none in Volume 2. Vercel + Supabase cloud for Volume 3's hosted build, free tiers until it matters; Supabase Auth and Storage are that build's. Background jobs deferred; provider sync is on demand

## Core model (shape only; the Volume 1 schema chapter decides columns)

- Media item: type-agnostic core (title, type, release date, franchise refs, provider ids) plus type-specific metadata. Relations between items: adaptation-of, contained-in (a story inside an issue, an episode inside a season)
- Edition: child of a media item (a printing, a cut, a platform release). For comics, an edition has contents: the issues it collects
- Shelf: ordered list with one level of sections. Entries point at media items; each entry carries a status (unmarked, done, skipped) so skipped stays visible
- Occurrence: one read, watch or play of an item, with dates, status, star rating. Journal entries hang off occurrences and carry an optional progress anchor (page, episode, issue, chapter) so an entry can say where in the work it was written. Read and watched are computed from occurrences, never from the collection
- Copy: an owned thing. Points at an edition, carries format, condition, acquired date, note. Ownership of an issue is derived through the copy's edition contents and shown as "owned via <copy>"; the note field covers edge cases
- Shopping view: items on my shelves with no copy. Derived, not stored. "Wishlist" is not a word in the product
- Franchise: entity seeded by providers (TMDB collections, IGDB franchises, Metron series). Stored from Volume 1, surfaced as suggestions in 1.0+
- Visibility: on every table that holds user content (shelves, entries, occurrences, journal entries, copies) from the first migration. Account tables such as profiles don't carry it. Private by default

## Calls made (with reason)

- 2026-11-05 Volume 2 is the sideloaded app, local-first, nothing hosted; the hosted nook with the social layer is Volume 3. Reverses "fully hosted, nothing to self-install" (2026-10-16). Reason, L: the cloud side brings infrastructure to own and a cost before there is anyone to pay it, while a sideloaded app is free to deploy, gets something publishable sooner, and brings feedback on the core feature set from people using it; an app interface was always the goal and it has to be cleanly usable on a phone. The same tables both places (PGlite on device, Postgres hosted, the same migrations) so the move later is an export and an import. L is the only user until the stretch says otherwise; deployment strategy is talked through after L has had an early build in hand (Volume 2 design talk)
- 2026-11-05 Every provider key is user-entered on the device, on a Providers settings screen with a Test button; no key ships in a build. Comic Vine's limit is 200 requests per resource per hour per key, so one shared key is one budget for everyone who installs; TMDB's limits are per IP, but its key is a non-commercial one either way, and L accepts Comic Vine will need replacing altogether, so a user's own key is the right starting place. Bring-your-own is the design, not a fallback (Volume 2 design talk)
- 2026-11-05 The catalog is non-commercial under the keys we hold: TMDB's free key is for projects whose primary purpose isn't revenue, and a commercial licence is negotiated with their sales team, price unpublished; Comic Vine's terms are non-commercial only with no licence offered. So a hosted nook that earns anything (a paid app, purchases, ads) opens with a TMDB quote and a different comics source, Volume 3's first two reads (Volume 2 design talk)
- 2026-11-05 Builds come first in Volume 2 and every chapter after Ch 2 is Browsed on the phone by installing its build over the last, the data carried; the phone is never reset. Reason, L: that is the test of the data, and it gets the app in hand sooner. One signing keystore, made once and backed up, since Android refuses an install-over from a different key (Volume 2 design talk)
- 2026-11-05 A Volume closes only on a green Nightly, all three browsers, and the close PR's description names the run. Per-PR CI runs Chromium alone, so its green never covered Firefox or WebKit; Ch 1.7 ended with Nightly red on `dev` and nobody looking (Ch 1.8 design talk). A chapter with no screen and no door (a hotfix, a close-out) runs Run 1 and its one Signature in one session, the Cartographer writing section 2, the cut and section 3 in one spawn (Ch 1.8)
- 2026-11-04 One post owns a copy: `{ edition }` when the printing is known, else `{ item, format }` and the server finds the work's one edition of that format or makes one in the same transaction; two of that format is a 409 that says to pick one on the page. A film on disc has no edition until someone holds it, and "add an edition first" is a step nobody should take (Ch 1.7 design talk)
- 2026-11-04 Formats narrowed per type and form at the API: book paperback, hardcover, ebook, audiobook; comic issue, one-shot and anthology floppy, digital; collected tpb, hardcover, omnibus, digital; backup none; film and TV dvd, blu-ray, 4k, digital. Condition is five words (new, fine, good, fair, poor) or blank, text with a check as every enumeration is; a grade scale is a Deferral (Ch 1.7)
- 2026-11-04 Two copies of one printing are two rows, each with its own condition and note: a reading copy and a sealed one are different things on the shelf (Ch 1.7)
- 2026-11-04 Owned via is read, never written: a work is held when you hold a copy of one of its editions, via when you hold a copy of an edition whose contents list it; a backup story is via when its contained-in host is held or via, one hop, since the host's pages hold it. The one place narrative and physical containment coincide (Ch 1.7, L)
- 2026-11-04 The shopping view is derived: every work on any of your shelves that is neither held nor via, backups left out (you buy what prints them), skipped entries kept (skipped is the shelf's reading word), a work on two shelves listed once under the first, grouped by shelf and section. Nothing stored; "wishlist" stays out of the vocabulary (2026-10-16 stands) (Ch 1.7)
- 2026-11-04 Mark owned from the series page: a tick per issue makes a floppy copy, an untick removes the newest one, asking once when it carries a condition or a note. The 2026-10-30 Deferral taken; floppy is the series page's one format, a trade of a single issue is the item page's business (Ch 1.7)

- 2026-11-03 Dates and timestamps bind through one shared Zod schema that states Postgres's range: no year 0, and a zone no further than 15:59 from UTC. Zod's ISO shapes admit what Postgres refuses, so each route that bound its own date answered a valid-looking input with the database's 500 (1.6.1 R1, R2; Ch 1.6 Afterword)
- 2026-11-03 A row a mutation answers carries its `updated_at` as the version the page compares against: a read's `PATCH` answers with `updatedAt` (UTC text with microseconds), the page's own read carries the same, and a control holding a clicked value shows the newer of the two. Without a version, a refresh that rendered before a later click put the old stars back, and a later write in another tab hid behind this tab's answer (1.6.2 D3, L at sign-off)
- 2026-11-02 One open read per work: at most one `in_progress` occurrence per owner and item, a partial unique index, a second one a 409 that says to finish or abandon the open read. A read is one time through; two open at once is a data-entry slip, not a state anyone means (Ch 1.6 design talk)
- 2026-11-02 The word follows the type: a read for a book or a comic, a watch for a film or a show; a play waits for games. One function gives every label, so the sheet, the card, the shelf's offer and the counts agree (Ch 1.6)
- 2026-11-02 Anchor kinds are narrowed per type at the API, as the Ch 1.1 vocabulary note promised: book page and chapter, comic issue page, collected comic issue and page, TV episode, film none. The pill prints "p. 112", "Ch. 7", "S02E03" as typed, "#7" (Ch 1.6)
- 2026-11-02 Stars are set any time on the read's card, not only at done; a work's shown stars are its latest starred read's; a shelf's or a section's star is the mean over its works that have one, to one decimal, with how many that is. Stars are a quick note (2026-10-16), so the quickest place to leave one is the card, and the shelf reports what the journal holds without inventing a rating of its own (Ch 1.6)
- 2026-11-02 Journal entries are plain text with line breaks kept, no markdown in alpha; `written_at` is settable, since a journal catches up on paper first (Ch 1.6)
- 2026-11-02 A Journal page at `/journal`: every entry across every work, newest first, 50 a page by keyset. The product says "journal, not review", so the journal has a page of its own and not only a section per work (Ch 1.6)
- 2026-11-02 Done on a shelf offers to log the read once, after the click the server has answered, under the row: Log or Not now. The status stays the shelf's and writes no read on its own (2026-10-30 stands); the offer is the shortcut, not the rule (Ch 1.6)
- 2026-11-02 Deleting a read deletes its entries, and the confirm says how many. An entry hangs off a read by design (2026-10-16); an orphan would be an entry about nothing (Ch 1.6)
- 2026-11-02 The item page's own sections come first: Journal under the facts, then On your shelves, then the catalog's Collected in, Editions and Connected. What you did with the work sits above what the catalog knows about it (Ch 1.6)
- 2026-11-02 `GET /api/v1/shelves?items=` takes at most 200 ids, and a sheet asking about a longer run asks in chunks of 200 and adds up `has`. The session cookie (about 3.3 kB) shares Node's 16,384-byte header cap with the URL, so the spec's 500 never reached the route signed in and about 345 was the real ceiling; 200 leaves room for a fatter cookie. A series past 1,000 issues, or a slow sheet, is the trigger for a `?series=` form (1.5.3 B1, L)

A shelf with no sections keeps "At the end". The add sheet's lede says "It goes after what's already there, in the section you pick or outside the sections." (1.5.3, the Raccoon's note, L at sign-off)

- 2026-10-30 A shelf's order is integer positions 1..n across the whole shelf, renumbered by the server on every write that moves anything, in display order: unsectioned entries first, then each section by its position; a move is "into this section at this index" and the server does the numbering (Ch 1.5)

- 2026-10-30 Adding a work already on the shelf skips it and says so, never an error, so a whole run can be added to a shelf that holds part of it (Ch 1.5)

- 2026-10-30 The 1.4.3 Deferral is taken in Ch 1.5: Add on the series import sheet with the hand-entered select left on No says what it is about to do and asks once (Ch 1.5)
- 2026-10-30 Shelves are private with no visibility control until Volume 2; the column is set on create (Ch 1.5)
- 2026-10-30 A hand-entered run's parenthetical publisher gates its match: "(Mirage) Vol. 1" matches a Mirage volume and never a TM-Semic or Dreamwave one with the same name and a year within 1; a parenthetical that is only a year ("(1984)", Comic Vine's own way) names no publisher and gates nothing. The gate is an exact fold, so "(IDW)" doesn't meet "IDW Publishing" (a Deferral until a real run trips it). From the 1.4.1 recordings, which showed two strangers the fixture never would (1.4.1 Q2, L)
- 2026-10-30 A collected group matches a volume only when what its editions hold has a series text whose fold the volume's name contains whole: the five Ultimate Collections (holding Mirage Vol. 1) meet "Teenage Mutant Ninja Turtles: The Ultimate Collection" and not "New X-Men Ultimate Collection"; a group whose editions hold nothing with a series text never matches (1.4.1 Q1, L)
- 2026-10-30 A run attaches only to comics of its own form: collected editions to `collected`; single issues to `issue`, `one-shot` and `anthology` (a host book); never to a `backup`, which is a story inside another comic. The server refuses before any write, so a wrong radio on the sheet is a 409 and not 62 phantom hardcovers (1.4.2 B1 and D8)
- 2026-10-30 A hand-entered run that numbers two comics the same is a 409 naming the number, not "the first wins": an issue can't tell which it is, and the other would be stranded in a group no search offers again. The fixture's Savage Dragon #2 is the case (1.4.2 D9)
- 2026-10-30 Saving an edition's contents keeps every comic it already held at its place in the printing and appends the new ticks in the picker's order; a Save that changed nothing writes the order it found. The route is unchanged: the array's order is the printing's (1.4.3 D3)
- 2026-10-29 Comics come from Comic Vine, not Metron. Metron's commercial-use terms say an app used by many people needs each user to hold their own Metron account, and a second sign-in after Fluxnook's own is a product rule broken; Comic Vine is one key per site, and its public pages matched the Mirage fixture series for series (1984 Mirage 62, 1993 Mirage 13, 1996 Image 23, Tales 1987 7, The Ultimate Collection 7 volumes). The costs, recorded so they aren't surprises: Comic Vine's API is "strictly for non-commercial use", re-read if Fluxnook ever charges; its attribution is per page, so every page showing Comic Vine data links back to the record it came from, not only the footer; its rate is 200 requests per resource per hour; a trade's contents are prose, so edition contents are filled by hand in this chapter. `item_sources` is per source, so Metron can be added beside Comic Vine later without a migration (Ch 1.4 design talk)
- 2026-10-29 A Comic Vine volume is a `series` row (name, volume, year began, publisher, kind, source key), a catalog table like `franchises`; `item_comics.series_id` points at it and the `series` text stays for manual items and as the held label. Franchise is not seeded from Comic Vine: TMNT the thing is a franchise, "Teenage Mutant Ninja Turtles (Mirage) Vol. 1" is a series, and the Roadmap's "Metron series" in the core model meant the latter (Ch 1.4)
- 2026-10-29 A comic series matches the catalog on its folded name after a trailing "Vol. n" and a parenthetical publisher are stripped, and the year of the catalog group's earliest issue within 1 of the volume's start year; never on the volume number, which Comic Vine doesn't carry. Inside an attached series, an issue attaches by number; a collected edition attaches by the trailing number of its held title. The sheet shows the rule, the server holds it, as 1.2 S1 says (Ch 1.4)
- 2026-10-29 Comic Vine doesn't know a run of floppies from a run of trades: both are a volume of issues.
