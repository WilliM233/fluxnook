## 0. Spec (Nookkeeper)

**What this chapter delivers.** Fluxnook runs on L's phone and PC with no server anywhere: a shell (Tauri 2 or Capacitor, chosen at the census) around a web view, with a Postgres of its own (PGlite) that the repo's migrations build on first launch. Not the app yet: one stub page that prints the migrations applied, adds a shelf by name and lists the shelves. The point is what's around it: a signed Android build and a Windows build out of CI on every PR and every tag, and a second build installing over the first on the phone with the shelf still there. From here every chapter is Browsed on the phone by installing its build over the last one.

**Run.** Run 1 maps and cuts as House Rules 1b. The Cartographer makes the shell call (A1) at the census from a desk read of both shells' current docs, measured on A1's points, and names it as a Stop-for-L only if the measures tie. Expect two Signatures: the stub on PGlite, then the shell and the builds; one is a valid cut if the census says so. The Signature that proves the install-over (A5) is the door, QA Fable.

**Acceptance.**
- A1 The shell is chosen at the census and section 2 says why, measured on: Android and Windows from one project; what the shell's Android WebView gives PGlite to persist in (IndexedDB, OPFS); a GitHub Actions build on `ubuntu-24.04` (and `windows-latest` where the shell needs it) inside 30 minutes; apk signing with a keystore CI holds; what the dev box has to install for the Binder to build and run locally. Whichever it is, the web code is the repo's (TypeScript, Tailwind, the Deep Field tokens), not a second UI stack. The Roadmap's Stack block takes the answer at the Afterword
- A2 PGlite holds the schema. The 15 migrations under `supabase/migrations` apply on the device on first launch through Drizzle's migrator reading `meta/_journal.json`, with one exception named by name: `20261016202031_profiles_on_signup.sql` is the trigger on `auth.users`, Supabase's schema and not ours, so the device migrator skips it by a rule that names the file, and the app makes the device's one profile row itself, so every `owner` column has its row. No migration is edited; the hosted build applies all 15 as it does today. Observable: a Vitest test applies the migrations to a PGlite in Node and reads 14 applied and the tables `src/db/schema.ts` names; the stub page prints "14 migrations · <n> tables" with n from the test
- A3 The stub page. One route in Deep Field tokens: A2's counts, the version from `package.json`, a field that adds a shelf by name (a row in `shelves`, the device profile its owner, visibility private) and the shelves listed. Nothing else; no screen is drawn
- A4 Persistence. Swipe the app away, open it: the shelves are there. On the phone and on Windows, each with its own data
- A5 Install-over. Build B (a version bump and a label the page prints) installs over build A on the phone with `adb install -r`, no uninstall, and opens with build A's shelves. The signing keystore is made once by the Binder (`keytool`); its base64 and its password are GitHub secrets (`gh secret set`); L keeps the backup (Hands). A different keystore is a wipe for every phone that has the app, and the README's install note says so
- A6 CI. `.github/workflows/build.yml`: on `pull_request` and on a push of a tag `v*`, builds the signed apk and the Windows build; both uploaded as artifacts on every run, and attached to the tag's GitHub Release when it has one (Volume and hotfix tags do; chapter tags are pre-releases without one, so their artifact is the download). The run's URL in section 5. The existing six CI jobs untouched
- A7 Tests. Vitest: A2's migration test; the shelf add as a function against PGlite. Playwright: the stub page in Chromium against PGlite in the browser, add a shelf, reload, still there. Every existing suite green unchanged
- A8 Docs. `docs/STACK.md` gains the shell and PGlite with versions; README gains "Install on a phone" (adb, the apk, the keystore note); `docs/releases/2.1.md`; `package.json` to `0.2.0-ch.1.1`; `scripts/browse/2.1.1.sh` (and `2.1.2.sh` if the cut makes two). Every new dependency has its line in the plan saying why and what it replaces; expect `@electric-sql/pglite` and the shell's packages, nothing else

**Calls this chapter depends on.** Roadmap Calls 2026-11-05: Volume 2 is the sideloaded app, local-first, nothing hosted; every provider key is user-entered on device; the catalog is non-commercial under the keys we hold. 2026-10-16: data model before stack; the server is the only database client (stands for the hosted build; on device the app process is the only client, the same rule one layer down); private by default. House Rules Git: no secret-shaped value is committed. House Rules step 7 (this spec's addendum): the phone Browse.

**Hands.** L's prerequisites, each with its check, which the Binder's step 1 runs first:
- An Android phone with Developer options and USB debugging on, plugged in: `adb devices` prints the phone as `device`
- Android platform-tools on the dev box, on PATH: `adb version` prints a version (the zip from developer.android.com/tools/releases/platform-tools, nothing else from the SDK)
- `gh` signed in, for the secrets and the artifact download: `gh auth status` prints "Logged in"
- A place for the keystore backup (the password manager): L's hand at A5's step, not a check
- Whatever A1's shell needs for a local build beyond `npm install` (Rust and the Android NDK for Tauri, the Android SDK for either): the census names it, and L's call at plan review is whether the dev box gets it or CI is the only builder of the apk, with the Binder running the stub in a browser and the phone as the Browse
- Docker Desktop up and the stack running, as every chapter: `npx supabase status` prints the API URL

**Browse.** Git Bash, from a clean tree, the phone plugged in. The script: the tree clean; A2's test green, 14 applied; the stub's e2e green; `adb devices` showing the phone; the PR's two artifacts fetched with `gh run download` into `browse-results/` (build A and build B; the Cartographer's steps say how B is made from the same branch, a label the page prints is enough). By hand: `adb install browse-results/<A>.apk`; open Fluxnook on the phone: "14 migrations · <n> tables", the version; add a shelf "King": one shelf listed; swipe the app away, open it: King is there; `adb install -r browse-results/<B>.apk`; open it: the page prints B's label and King is there. On Windows: run the build, the same three steps on their own data. That is the walk, five minutes; a phone that has to be wiped to pass is a blocking finding.

**QA model.** Fable on the Signature that carries A5 (a person's data across an upgrade is the door); Opus for the rest.

**Out of scope.** The app itself on the phone (Ch 2.2 moves the pages and services into the shell; until it lands the real app is still the server one). Any screen. Providers, sign-in, export, covers. iOS. The Play Store. Supabase and the hosted build aren't touched. SQLite: plan B only if PGlite fails A4 on the phone, and then a Roadmap call and a re-cut, not a step.

## 1. Feasibility (Nookkeeper)

- **What exists** (`dev` at `a2774d0`, read on disk 2026-11-06). The database client is one function, `src/db/client.ts` `createDb()` over the `postgres` driver, with `serverDb()` keeping one pool per process; Drizzle's schema is `src/db/schema.ts`. 15 migrations under `supabase/migrations`, plain SQL with Drizzle's `--> statement-breakpoint` markers and `meta/_journal.json`, applied by the Supabase CLI today; `scripts/db-check.mjs` proves schema and migrations agree. What's in them that PGlite has to run: `gen_random_uuid()` ten times (core Postgres since 13; PGlite is 17), two plpgsql functions and their triggers (`updated_at`, `occurrences_one_open`; PGlite ships plpgsql), `uuid` columns throughout, no extensions created. One migration is Supabase's: `20261016202031_profiles_on_signup.sql` creates a `security definer` trigger `AFTER INSERT ON auth.users`, which no PGlite has; A2 skips it by name. Every content table's `owner` references `public.profiles(id)`, so one local profile row is all the device needs
- **The size of Ch 2.2, measured here so its cut starts from numbers.** 39 files under `src/app/(app)` import a `src/lib` service, 13 import `@/db` directly, 30 files under `src/lib` import `@/db`, and 13 client components `fetch` `/api/v1`. That's the seam Ch 2.2 cuts; this chapter doesn't touch it. `next.config.ts` sets no `output`, and the stub needn't be Next at all: the Cartographer may make it a plain page in the shell project or a Next static export of one route; Ch 2.2 decides the app's build
- **PGlite.** Postgres in WASM, about 3 MB gzipped; Drizzle has a `pglite` driver and its migrator reads the same journal. In a browser it persists to IndexedDB (`idb://`) or OPFS (a worker, and cross-origin isolation a shell's custom scheme may not give). IndexedDB is the floor and what A4 is measured on first. The one real unknown in the chapter is this inside an Android WebView: quota, WASM memory, a kill mid-write. A4 on the phone is the test; a fail is the SQLite plan B above
- **The shells.** Tauri 2: Rust core, the system WebView, Android and Windows from one project; CI needs Rust and the NDK, so builds run longer; signs the apk through Gradle. Capacitor: Gradle and Android System WebView; a Windows build has no first-party story (Electron through a community package). Both have published Actions recipes. The census reads both as they stand today and fills A1's five measures; the Windows line is the one most likely to decide it
- **Risk, medium.** PGlite in the WebView (above). The CI toolchain is the second: both shells build on hosted runners by published recipe, and A6's 30 minutes is the cap. The dev box is the third: Rust plus the NDK is a large install, and the Hands line leaves it as L's call. Likely cut: two Signatures, 2.1.1 `pglite-stub` (A2, A3, A4 in the browser, A7) and 2.1.2 `builds` (A1's project, A5, A6, A4 on the phone and Windows, A8, the exit Browse)
