# Plan: 1.1 Schema

Issue: #<n> · Branch: `chapter/1.1-schema` · Volume: Volume 1: Alpha

## 0. Spec (Nookkeeper)

**What this chapter delivers.** The tables. Every piece of the Roadmap's core model becomes a Postgres table through Drizzle and plain SQL migrations: the shared catalog (items, their type-specific columns, sources, relations, editions with contents, franchises) and a person's own content (shelves with sections and entries, occurrences, journal entries, copies), each content table carrying `visibility`, private by default. A loader reads the three Volume 0 fixtures into those tables for one user, and CI proves the counts. No page changes; the nook is still empty. Every chapter after this one inherits these tables.

**Acceptance.**
- A1 Catalog tables, shared by every user, no `visibility`: `items` (`type` in `film`/`book`/`comic`; `title`; `form`, null for films, checked per type: books `novel`/`novella`/`collection`/`story`/`series`, comics `issue`/`one-shot`/`backup`/`collected`/`anthology`; `released_on date` with `released_precision` in `day`/`month`/`year`, both null or both set; `source_note`, null allowed; `created_by` → `profiles`, null for loader and provider rows; `created_at`, `updated_at`), `item_books` (`item` pk, `author`), `item_comics` (`item` pk, `series` null, `series_kind` null in the six kinds, `number` null), `item_sources` (`item`, `source`, `key`, `url` null; unique on `(source, key)`), `item_relations` (`from_item`, `to_item`, `kind` in `adaptation-of`/`contained-in`; pk on the three; `from_item <> to_item`), `editions` (`item`, `format` in `floppy`/`tpb`/`hardcover`/`omnibus`/`paperback`/`ebook`/`audiobook`/`dvd`/`blu-ray`/`4k`/`digital`, `title` null, `released_on`/`released_precision` as on items), `edition_sources` (as `item_sources`, for an edition), `edition_contents` (`edition`, `item`, `position`; pk `(edition, item)`), `franchises` (`name`), `franchise_sources`, `item_franchises` (pk `(item, franchise)`). No `item_films` until TMDB brings a film column (Ch 1.2)
- A2 Content tables, each with `user` → `profiles` and `visibility` in `private`/`unlisted`/`public` default `private`: `shelves` (`name`, `description` default `''`, `source_url` null), `shelf_sections` (`shelf`, `name`, `position`; unique `(shelf, name)`), `shelf_entries` (`shelf`, `section` null, `item`, `position`, `status` in `unmarked`/`done`/`skipped` default `unmarked`; unique `(shelf, item)`; a composite foreign key `(section, shelf)` → `shelf_sections (id, shelf)` so an entry can't sit in another shelf's section), `occurrences` (`item`, `status` in `in_progress`/`done`/`abandoned`, `started_on` null, `finished_on` null, `stars numeric(2,1)` null, checked to half steps 0.5–5.0), `journal_entries` (`occurrence`, `written_at` default now, `body`, `anchor_kind` null in `page`/`chapter`/`episode`/`issue`, `anchor_value` null, both null or both set), `copies` (`edition`, `condition` null, `acquired_on` null, `note` default `''`). `shelf_sections` and `journal_entries` reach their user through their parent and carry no `user` column; `shelf_sections` carries no `visibility` (the shelf's is the section's); `journal_entries` does. `created_at` and `updated_at` on every table, `updated_at` kept by one trigger function
- A3 Deletes: a `profiles` row going cascades to every content row it owns, through shelves to sections and entries, through occurrences to journal entries; a catalog row restricts while any content row points at it (`shelf_entries.item`, `occurrences.item`, `copies.edition`); `item_relations`, `edition_contents`, `item_sources`, `item_franchises` and `editions` cascade from their item; an edition restricts while a copy exists
- A4 Migrations: generated from `src/db/schema.ts` by `npm run db:generate` into `supabase/migrations`, plus one `--custom` file for the `updated_at` function and its triggers. Each file opens with its `-- Down:` block, run once inside `begin; … rollback;` against local (the migrations skill). `npm run db:check` clean. `npx supabase db reset` applies them from empty. Every content table is `visibility`-bearing and nothing is granted to `anon` or `authenticated` (`config.toml` unchanged)
- A5 A Drizzle runtime client at `src/db/client.ts` on `drizzle-orm/postgres-js` reading `DATABASE_URL`; `postgres` moves from devDependencies to dependencies, STACK row rewritten. Closes the Ch 0.2 Deferral (trigger: the first chapter that queries an app table; this is it)
- A6 `npm run fixtures:load -- --user <email>` reads every file under `supabase/seed/fixtures/`, validates each against `src/fixtures/shape.ts`, and in one transaction writes: all items from all files first (an item's fixture id `<source>:<key>` is its `item_sources` row; `year`/`month` become `released_on` + precision, `source_date` is appended to `source_note` for comics), then relations, editions (fixture edition id → `edition_sources`), contents, then the user's rows: shelves (fixture `date` → `created_at`), sections, entries, copies, occurrences. `gaps` are printed, never loaded. The user is found by email in `auth.users` and must have a `profiles` row
- A7 Idempotent by construction: catalog rows upsert on their source key, so a second run adds no catalog row. Content rows are written only to a user who has none; `--replace` clears that user's shelves, occurrences and copies first and writes them again. Run twice with `--replace`, the counts in A8 are unchanged; run without it against a user with content, it stops and says so before writing anything
- A8 After `npx supabase db reset` and one load: 454 `items` (61 film, 27 book, 366 comic), 454 `item_sources` (61 `letterboxd`, 393 `manual`), 27 `item_books`, 366 `item_comics`, 125 `item_relations` (62 `adaptation-of`, 63 `contained-in`), 5 `editions`, 5 `edition_sources`, 37 `edition_contents`, 0 `franchises`; for the user: 3 `shelves`, 14 `shelf_sections`, 398 `shelf_entries` (61 + 11 + 326, all `unmarked`), 26 `occurrences` (all `done`, no dates, no stars), 0 `journal_entries`, 5 `copies`. `tests/db/fixtures-load.test.ts` asserts every number against the fixture files, not against literals, and runs in CI's `test:db` job after a signup
- A9 Seen red, each once and reverted: the `visibility` default removed from one content table in `schema.ts` → `db:check` red; a shelf entry inserted into another shelf's section → the composite key rejects it; `stars = 4.3` rejected and `4.5` accepted; a `profiles` row deleted → that user's copies, occurrences and shelves are gone and the catalog counts are unchanged; `fixtures:load` without `--replace` against a loaded user → exits non-zero, nothing written
- A10 README gains a Data model section (the two halves, visibility, "owned via" as a query over `copies → editions → edition_contents → items`, the loader and `--replace`); `docs/STACK.md` rows for `postgres` and any runner the loader needs; the migrations skill's Visibility paragraph names the content tables as they now exist
- A11 Volume 0 carry-ins, in this chapter's spec commit: the Roadmap's Volume 0 close line (`2026-10-23 Volume 0 closed, v0.0.0, PR #60`) and the House Rules Git addendum (a Volume tag and a hotfix tag each get a GitHub Release whose notes are the PR body; chapter tags are pre-releases and get none). `package.json` to `0.1.0-ch.1` by the Scribe at sign-off

**Calls this chapter depends on.** Roadmap core model, as written. Roadmap 2026-10-16: visibility is a column on content tables from the first migration, not on account tables; occurrences and journal entries hang off the item, never the copy; half stars, stars on the occurrence; the server is the only database client. Roadmap 2026-10-23: a work carries its original date and an edition its own; a story is a `book` with a `form`; a collected edition is a `collected` work with an edition and contents, ownership derived through contents; relations point across fixture files; the Dark Tower stays a `book` with form `series` until the franchise entity exists (it exists after this chapter; the row stays as it is until Ch 1.3 brings a provider). This chapter's calls (2026-10-23, Ch 1.1 design talk, Roadmap Calls): type-specific columns are child tables, not jsonb, and a column two types share lives on `items`; every enumeration is `text` with a check constraint, never a Postgres enum; the catalog is global and provider-deduped, with `created_by` for manual rows; `item_sources` is the identity table and `manual` is a source like any provider; `released_on` + `released_precision`; the show is the item, season and episode are the anchor; relations carry no position until a feature reads one; visibility is `private`/`unlisted`/`public`; the anchor is kind + text; shelf positions are integers renumbered on move; one edition-format vocabulary across types, narrowed per type at the API; no soft delete, user delete cascades, catalog restricts; `source_note` is kept and comic `source_date` folds into it; a fixture shelf's date is its `created_at`; occurrence status is `in_progress`/`done`/`abandoned`; journal entries exist as a table with zero rows

## 1. Feasibility (Nookkeeper)

- **What exists.** `src/db/schema.ts` holds one table, `profiles` (`id` → `auth.users` cascade, `display_name`, `created_at`); two migrations, `20261016202027_profiles.sql` and `20261016202031_profiles_on_signup.sql`, both with Down blocks; `drizzle.config.ts` writing to `supabase/migrations` with the Supabase prefix; `npm run db:check` proving schema and SQL agree offline; `tests/db/` with the `postgres` driver (3.4.9, devDependency, test-only), `vitest.db.config.ts` loading `DATABASE_URL` from `.env.local`, and CI's `test-db` job bringing the stack up; `config.toml` with `public` out of `[api] schemas` and `auto_expose_new_tables = false`. No runtime client, no app table beyond `profiles`.
- **The fixtures, measured on `dev` at `0af7665`** (read on disk 2026-10-23, counts taken after the shape's rules, cross-file resolved). `king-films`: 61 items, all `letterboxd:` ids with the matching `providers.letterboxd` URL, 1 flat shelf of 61. `king-books`: 27 items, all `manual:`, forms 8 novel / 16 story / 1 collection / 1 novella / 1 series, 78 relations of which 62 `adaptation-of` point at `king-films` items and 16 `contained-in` stay in the file, 1 shelf of 11, 1 gap. `tmnt-mirage`: 366 items, all `manual:`, forms 253 issue / 47 backup / 26 one-shot / 35 anthology / 5 collected, `series_kind` 207 ongoing / 29 minor / 20 mini-series / 9 crossover / 9 tie-in / 5 micro-series / 87 null, 26 distinct `series` strings, 47 `contained-in`, 5 editions (all hardcover) holding 37 ids, 5 copies, 26 occurrences, 1 shelf of 14 sections and 326 entries, 9 gaps. Dates: 98 items year-only (61 films, 27 books, 10 comics), 342 year + month, 14 null (the 9 gap rows and the 5 Ultimate Collections). No item is on a shelf twice in any file; no issue is in two editions; no part is contained-in two wholes; section names are unique per shelf. These are the facts A8 and the constraints in A1–A2 rest on.
- **Child tables vs the data.** Films carry nothing past the core (title, year, providers), so `item_films` would be an empty table today; it waits for Ch 1.2. `form` is on books and comics with disjoint vocabularies, so it lives on `items` with a check over `(type, form)` pairs. Comic `month` folds into `released_on` + `released_precision`; `year` null with `source_date` set is the 14-row case, and A6's fold into `source_note` keeps the cell.
- **Drizzle can write all of it.** `check()` in `pgTable`'s third argument (drizzle-orm 0.45), composite `foreignKey({ columns, foreignColumns })` for the section key, `numeric("stars", { precision: 2, scale: 1 })`, `unique()`, `primaryKey({ columns })`. drizzle-kit 0.31 emits check constraints and composite keys. What it will not write is the `updated_at` trigger: that's the `--custom` file. Expect two migration files, one generated (the whole model; the Cartographer may split by half if the Down block gets long) and one custom; the generated file's Down is the drops in reverse dependency order, the custom's is the triggers then the function.
- **The loader runs TypeScript.** It imports the Zod shape and the Drizzle schema, both `.ts`, and `scripts/` is `.mjs` today. Node 22 strips types natively (`--experimental-strip-types` on 22.6–22.17, unflagged from 22.18; `@types/node` pins 22.20.5 so the local Node is in range, CI's `setup-node` version to be checked by the Cartographer); the alternative is `tsx` as a devDependency with its STACK row and the "why, replaces nothing" line. The Cartographer's call; either way `fixtures:load` is a `package.json` script.
- **Idempotency has two halves.** Catalog: `insert … on conflict (source, key) do update` on `item_sources`, with the item id read back; editions through `edition_sources` the same way; relations, contents and franchises on their primary keys. Content: there is no natural key for "the loader's occurrence of Vol 1 #1", and inventing one (a `loaded_from` column) would put the fixture into the product's tables. A7's rule avoids that: content loads only into an empty user, `--replace` empties first. CI's user is fresh every run.
- **The signup trigger and the loader's user.** `profiles` rows are made by `on_auth_user_created`; the loader looks the email up in `auth.users` and then `profiles`, and names both when either is missing. CI's `test:db` already signs a `db-<uuid>@example.com` user up through `signInWithOtp`; the load test does the same and passes that address.
- **Cascade shape, checked against the model.** `auth.users` → `profiles` (exists) → `shelves`, `occurrences`, `copies` (A2) → `shelf_sections`, `shelf_entries`, `journal_entries`. Catalog edges restrict: `shelf_entries.item`, `occurrences.item`, `copies.edition`. The one subtle edge is `editions.item`: cascade from the item is right (an edition is nothing without its work), and `copies.edition` restrict then protects the item through the edition. A9's profile-delete red is the proof the content side holds and the catalog side doesn't follow.
- **Rummage the Raccoon will want.** Defaults are the quiet failure: a `visibility` column that exists but defaults wrong passes every count. A test that inserts the minimum row into each content table and reads `visibility` back is cheap and specific. The composite section key is the kind of constraint that gets dropped when a schema is "simplified"; A9 keeps it honest. `--replace` on an email that isn't the one intended is the loader's only destructive path; the confirmation is the user's email echoed in the log line before the delete.
- **Volume 0 carry-ins.** A11's Roadmap and House Rules edits ride the spec commit, as queued at the Volume 0 close. Two Nookkeeper process lines from the Ch 0.6 Afterword apply to this chapter's review and need no file: the section 0 correction is verified on disk before it goes to the Binder, and feasibility counts are taken after the rules (done above, from the files).
- **Risk, moderate to high.** Fourteen tables in one chapter is the largest surface Fluxnook has shipped, and the names are permanent in the way nothing in Volume 0 was. The migration SQL itself is low-risk (generated, checked, reset from empty). The loader is where the order and the cross-file ids can go wrong, and A8 catches every miscount. The Pilot change above is the mitigation for the naming.
