## 0. Spec (Nookkeeper)

**What this chapter delivers.** The app exists and runs locally on the locked stack. A person can sign up with an email, get a magic link from the local mail catcher, click it, and land on an empty nook page that says it's theirs. Nothing else.

**Acceptance.**
- A1 `npx supabase start` then `npm run dev` brings the app up from a fresh clone with only `.env.example` copied to `.env.local`; README says exactly those steps and nothing the Scribe didn't run
- A2 `/` unauthenticated shows a sign-in form: email field, "send me a link" button. No password field anywhere
- A3 Submitting an email produces a magic link in the local mail catcher (Supabase's bundled Inbucket or Mailpit, whichever the pinned CLI ships); clicking it lands on `/nook`
- A4 `/nook` shows the signed-in user's email and the words "Your nook is empty" (exact copy is the Binder's; the state is the spec). A sign-out control returns to `/`
- A5 `/nook` unauthenticated redirects to `/`. `/api/v1/me` returns 401 unauthenticated and `{ id, email }` authenticated, Zod-validated response
- A6 A `profiles` table exists with one row per auth user (id FK to `auth.users`, display name nullable, created at), filled by a trigger on signup. This is the only app table this chapter adds; the core model is Volume 1 Chapter 1
- A7 `npm run lint`, `npm run typecheck`, `npm test` (Vitest) all pass with at least one real unit test (the `/api/v1/me` Zod schema), and `npm run test:e2e` (Playwright) passes with at least one test (A2 renders). CI wiring itself is Chapter 3
- A8 Every dependency version is exact in `package.json` (no `^`), and `docs/STACK.md` lists each pinned version with one line on why it's there

**Calls this chapter depends on.** Roadmap 2026-10-16: Supabase Auth email + magic link, custom auth ruled out; Zod route handlers under `/api/v1`, no server actions for mutations; Drizzle, RLS off; Tailwind + shadcn/ui, Vitest + Playwright, Biome.

**Hands.** Team runs it, except: L pastes the House Rules update (Chapter 1 Afterword lines) as the first commit on the branch, `docs: house rules from ch 1 afterword`.

**Browse.** In the dev checkout, `npx supabase stop` first; both clones share `project_id`, so two stacks collide. Fresh clone to a new folder. Follow README only. Sign up with a real address of yours; open the mail catcher; click the link; see your email on `/nook`; sign out; try `/nook` directly and get bounced; `curl -i localhost:3000/api/v1/me` and see 401. Then `npx supabase db reset` and confirm the app still comes up clean.

**Out of scope.** Any table from the core model. Any page beyond `/` and `/nook`. OAuth. Password sign-in. Profile editing. Hosting config, Vercel, CI workflows, fixtures (Chapter 3). Design system beyond shadcn defaults; the look is Volume 1's problem.

Risk: two migration folders is a known tangle; the Cartographer decides the single folder and writes it into the `migrations` skill under `.claude/skills/`.
- **`profiles` trigger.** A Postgres trigger on `auth.users` insert is the standard Supabase pattern; it must live in a migration, not be created by hand in Studio, or `db reset` loses it. A6's test is: reset, sign up, row exists.
- **Auth in route handlers.** Reading the session in `/api/v1/me` needs the Supabase server client with cookie handling for the App Router. The Cartographer picks the official helper package for the pinned Next major and notes it in STACK.md.
- **Playwright and the mail catcher.** A3 end to end would mean Playwright reading the catcher's API; that's Chapter 3's harness. This chapter's Playwright test is A2 only. A3 is Browse.

## 3. Steps (Cartographer)

**Shape choices** (one line why each).

- Layout: `src/app` (App Router), `src/lib/{supabase,api}/`, `src/lib/env.ts`, `src/db/schema.ts`, `tests/unit` (Vitest), `tests/e2e` (Playwright). Tests live under `tests/` because the Rummage lines in the plan template point there.
- Cache Components off: every page here reads the session cookie, and Cache Components would demand a Suspense boundary around each read with nothing to cache.
- `.npmrc` with `save-exact=true`: every later install, including the ones shadcn runs, writes exact versions, which is A8 by construction.
- Auth is PKCE with Supabase's default email template: the link returns to `GET /api/v1/auth/callback?code=…`, which exchanges the code and sets the cookie. No template override in `config.toml`.
- Auth mutations are JSON route handlers under `/api/v1/auth/` called with `fetch` from small client components (`CLAUDE.md`: no server actions for mutations). No browser Supabase client.
- `/` and `/nook` redirect in the page (server component); `src/proxy.ts` only refreshes the session.
- A signed-in visit to `/` redirects to `/nook`: nothing on the sign-in form is useful to a signed-in user.
- The callback lands only on `/nook`, or `/?error=link` on failure. No `next` parameter, so no open redirect.
- API error body is `{ "error": { "code": string, "message": string } }` from one helper in `src/lib/api/errors.ts`: a code for clients, a message for people.
- Any `getUser()` without a user, including an unreachable auth server, is a 401 on `/api/v1/me` and a redirect on `/nook`.
- `profiles.id` references `auth.users(id)` `on delete cascade`: without it, deleting an auth user fails on the FK.
- `src/lib/env.ts` parses the two public env vars with Zod through `readEnv(source = process.env)`: a fresh clone missing `.env.local` fails naming the variable, and the function is testable.
- Migrations: drizzle-kit generates, the Supabase CLI applies; never `drizzle-kit migrate` or `push`, which keep a second ledger. Each migration opens with a `-- Down:` comment holding the reversal SQL, because the Supabase CLI has no down migrations.
- Playwright: Chromium only, `webServer` runs `npm run dev` and reuses one already running. The browser matrix is Chapter 3's.
