## 0. Spec (Nookkeeper)

**What this chapter delivers.** The app exists and runs locally on the locked stack. A person can sign up with an email, get a magic link from the local mail catcher, click it, and land on an empty nook page that says it's theirs. Nothing else.

**Acceptance.**
- A1 `supabase start` then `npm run dev` brings the app up from a fresh clone with only `.env.example` copied to `.env.local`; README says exactly those steps and nothing the Scribe didn't run
- A2 `/` unauthenticated shows a sign-in form: email field, "send me a link" button. No password field anywhere
- A3 Submitting an email produces a magic link in the local mail catcher (Supabase's bundled Inbucket or Mailpit, whichever the pinned CLI ships); clicking it lands on `/nook`
- A4 `/nook` shows the signed-in user's email and the words "Your nook is empty" (exact copy is the Binder's; the state is the spec). A sign-out control returns to `/`
- A5 `/nook` unauthenticated redirects to `/`. `/api/v1/me` returns 401 unauthenticated and `{ id, email }` authenticated, Zod-validated response
- A6 A `profiles` table exists with one row per auth user (id FK to `auth.users`, display name nullable, created at), filled by a trigger on signup. This is the only app table this chapter adds; the core model is Volume 1 Chapter 1
- A7 `npm run lint`, `npm run typecheck`, `npm test` all pass with at least one real unit test (the `/api/v1/me` Zod schema) and one Playwright test (A2 renders). CI wiring itself is Chapter 3
- A8 Every dependency version is exact in `package.json` (no `^`), and `docs/STACK.md` lists each pinned version with one line on why it's there

**Calls this chapter depends on.** Roadmap 2026-10-16: Supabase Auth email + magic link, custom auth ruled out; Zod route handlers under `/api/v1`, no server actions for mutations; Drizzle, RLS off; Tailwind + shadcn/ui, Vitest + Playwright, Biome.

**Hands.** Team runs it, except: L pastes the House Rules update (Chapter 1 Afterword lines) as the first commit on the branch, `docs: house rules from ch 1 afterword`.

**Browse.** Fresh clone to a new folder. Follow README only. Sign up with a real address of yours; open the mail catcher; click the link; see your email on `/nook`; sign out; try `/nook` directly and get bounced; `curl -i localhost:3000/api/v1/me` and see 401. Then `supabase db reset` and confirm the app still comes up clean.

**Out of scope.** Any table from the core model. Any page beyond `/` and `/nook`. OAuth. Password sign-in. Profile editing. Hosting config, Vercel, CI workflows, fixtures (Chapter 3). Design system beyond shadcn defaults; the look is Volume 1's problem.

## 1. Feasibility (Nookkeeper)

The repo has no code, so this is about the ground the Cartographer will stand on rather than files.

- **Version lock is a research step, not a guess.** The Cartographer pins versions by querying the registry (`npm view <pkg> version`, `supabase --version`) on the day, writes them to `docs/STACK.md`, and the Binder installs exactly those. Risk: Next.js major boundaries move the App Router and route-handler conventions; the Cartographer notes which major it pinned and why.
- **Supabase CLI on Windows.** L develops in Git Bash on Windows with Docker Desktop. The CLI runs there; the Cartographer's census confirms Docker Desktop is up on the dev box before step 1, and the README's prerequisites name Docker Desktop and the CLI install path that works on Windows (npm or Scoop; not Homebrew).
- **Magic link locally.** Supabase local serves auth emails to its bundled mail catcher at a localhost port the CLI prints on `supabase start`. The README states that port. Risk: the redirect URL for the link must be in `supabase/config.toml` `[auth] additional_redirect_urls` or the link lands on the wrong origin; this is the step most likely to need a second try.
- **Drizzle against Supabase local.** Drizzle connects with the direct Postgres URL `supabase status` prints, not the API URL. Migrations are generated by `drizzle-kit` into `supabase/migrations` so `supabase db reset` applies them in order with Supabase's own. Risk: two migration folders is a known tangle; the Cartographer decides the single folder and writes it into the `migrations` skill under `.claude/skills/`.
- **`profiles` trigger.** A Postgres trigger on `auth.users` insert is the standard Supabase pattern; it must live in a migration, not be created by hand in Studio, or `db reset` loses it. A6's test is: reset, sign up, row exists.
- **Auth in route handlers.** Reading the session in `/api/v1/me` needs the Supabase server client with cookie handling for the App Router. The Cartographer picks the official helper package for the pinned Next major and notes it in STACK.md.
- **Playwright and the mail catcher.** A3 end to end would mean Playwright reading the catcher's API; that's Chapter 3's harness. This chapter's Playwright test is A2 only. A3 is Browse.
