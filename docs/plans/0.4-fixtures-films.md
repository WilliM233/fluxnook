## 1. Feasibility (Nookkeeper)

- **The file, measured.** ASCII, CRLF, 72 lines, no BOM. Parsed as one CSV stream (Python `csv`, RFC 4180): row 0 `Letterboxd list export v7`; row 1 `Date,Name,Tags,URL,Description`; row 2 the list itself (`2024-04-01`, `Stephen King Watch List`, no tags, `https://boxd.it/upKRw`, a quoted Description that spans lines and contains a blank line); row 3 empty; row 4 `Position,Name,Year,URL,Description`; rows 5–65 the 61 films. Trap: the blank line inside row 2's quotes means "split the file at the first blank line" picks the wrong place; the parser must honor quotes across lines and take the first empty *record* as the separator. Two film rows have multi-line descriptions (8 Chapelwaite, 28 Cat's Eye); row 52 has an empty one. URLs unique; no name+year collision (the three Carries differ by year). Description prefixes, for Chapter 5's benefit: Short Story 38, Novel 19, Novella 1, Series 1, Bachman Novel 1.
- **Parser.** Quoted multi-line fields rule out split-on-comma. Node 22 has no CSV reader in core. Either `csv-parse` (the standard; devDependency, exact pin, STACK row, "replaces nothing") or a short RFC 4180 reader inside the script. The Cartographer picks; A5's test covers either. Line endings: `.gitattributes` normalizes on commit, so the script sees LF on the runner and may see CRLF on a Windows checkout; it handles both.
- **Ids.** Two candidates. A slug from name and year (`carrie-1976`) is readable but is not a film identity: the same film in a second list must get the same id, and remakes with the same title and year exist. The boxd short id from the URL (`20ZQ`) is Letterboxd's own stable key for the film, unique and shared across every list, and is what a Letterboxd import at 1.0 would match on. The spec's requirement is cross-list identity; the Cartographer picks and says why. Either way the Letterboxd URL stays as the provider id.
- **Determinism.** Sorted keys, two-space indent, trailing newline, items in position order, shelf entries in position order. A5 compares bytes, so the writer's formatting is part of the contract and lives in one function.
- **Where things live.** `src/fixtures/shape.ts` is app code (the Volume 1 loader imports it), under `tsc` and Biome. The build script is `scripts/fixtures-build.mjs`, plain Node like `db-check.mjs`, so it can't import the TS shape without a loader; the script writes JSON and the Vitest test validates with the shape. That keeps the script dependency-light and the shape typed. `supabase/seed/fixtures/` is JSON only; `supabase/seed/raw/<source>/` is inputs only.
- **The test.** `tests/unit/fixtures-king-films.test.ts`: parse the JSON with the shape (red on a dropped `title`); run the build into `node_modules/.cache/fixtures/` and compare bytes with the committed file (red on an edited raw row). Milliseconds, no stack, so it stays in `npm test` and in the existing `test` job; no new CI context, protection untouched.
- **A6.** `timeout-minutes` on a step is already used in `ci.yml`'s install step; `tests/unit/rummage-workflows.test.ts` R6 checks job timeouts and is unaffected. A retry on top of the timeout needs either a shell loop or a pinned retry action; not in this chapter (Deferral below).
- **Risk, low.** `supabase/seed/` is a new top-level folder under `supabase/`; the CLI ignores it (`[db.seed] sql_paths` names only `./seed.sql`, which still doesn't exist, so the `no files matched` warning stays; out of scope as before). Biome's `files.includes` may need the new JSON folder ignored or formatted consistently with the writer; the Cartographer checks `biome.json`.

### Step 3: The CSV reader, test first
- Does: Write the RFC 4180 reader the build uses and its unit test.
- Touches: `scripts/fixtures/csv.mjs` (new), `tests/unit/fixtures-csv.test.ts` (new).
- How: the test first, importing `{ parseCsv }` from `../../scripts/fixtures/csv.mjs` (typechecks under `allowJs`, census). Cases: (1) `a,b,c\n1,2,3\n` gives `[["a","b","c"],["1","2","3"]]`, the trailing newline adding no record; (2) `"x, y","l1\nl2",z` gives one record `["x, y","l1\nl2","z"]`; (3) `"say ""hi"""` gives `say "hi"`; (4) the same text with `\r\n` as with `\n` gives equal records, and a `\r\n` inside a quoted field comes out as `\n`; (5) `a\n\nb\n` gives `[["a"],[],["b"]]`, an empty line is an empty record; (6) `1,2,` gives `["1","2",""]`; (7) an unterminated quote throws; (8) a character after a closing quote that isn't `,` or a newline (`"a"b`) throws.
