# Plan: 0.3 CI and the test harness

Issue: #52 · Branch: `chapter/0.3-ci-harness` · Volume: Volume 0: Foundations

## 0. Spec (Nookkeeper)

**What this chapter delivers.** Every PR into `dev` is checked by GitHub Actions before anyone reads it: lint, types, unit tests, the migration check, and the browser tests against a real local Supabase started in the runner. The test harness grows the two pieces every later chapter needs: a Playwright fixture that signs a fresh user in through the mail catcher, and a database test that talks to Postgres directly. Nothing a user sees changes.

**Acceptance.**
- A1 A workflow runs on every PR into `dev` or `main` and on every push to `dev`. It runs `npm run lint`, `npm run typecheck`, `npm test`, `npm run db:check`, `npm run test:db` and `npm run test:e2e`, the last two against a Supabase stack started in the runner with `npx supabase start`. Each gate is a step or job GitHub lists by name on the PR's Checks tab. No secrets: the stack's keys are the CLI's fixed local defaults, exactly as `.env.example`
- A2 `npm run db:check` fails when `src/db/schema.ts` and `supabase/migrations` disagree. It runs `drizzle-kit check` on the snapshots and then confirms `drizzle-kit generate` would write nothing (the "drizzle no changes" observable the Ch 0.2 handoff ran by hand). Seen red: a column added to `schema.ts` with no migration
- A3 Playwright signs in end to end: a test asks for a magic link for a fresh address, reads the mail from Mailpit's API at `http://127.0.0.1:54324`, follows the link, and lands on `/nook` showing that address. Closes the Ch 0.2 Deferral "Playwright through the mail catcher"
- A4 The sign-in from A3 is a Playwright fixture (the Cartographer names it) that any later spec imports to get a signed-in page for a fresh user. A3's test is written against it, and its doc comment is enough for the next chapter to use it without reading its body
- A5 A database test: after `npx supabase db reset`, signing a user up creates exactly one `profiles` row whose id is the auth user's id. Runs as `npm run test:db`, which needs the stack up; `npm test` stays stack-free. Closes the Ch 0.2 Deferral "Automated A6 check". Seen red: the trigger dropped
- A6 A nightly workflow runs the whole Playwright suite on `dev` across Chromium, Firefox and WebKit, and can also be started by hand (`workflow_dispatch`). The PR workflow runs Chromium only. The `playwright.config.ts` comment "the browser matrix is Chapter 3's" comes true
- A7 Branch protection on `dev` and `main` requires the PR workflow's checks to pass before merge. Set by L from a command block after the first green run names the checks
- A8 README gains a short CI section: what runs on a PR, the one local command that runs the same gates (`npm run check` or the Cartographer's name), and what to do when a check is red. `docs/STACK.md` gets a row for every package and every Action added, each pinned exactly (a SHA or an exact tag for Actions; the Cartographer picks and says why)

**Calls this chapter depends on.** House Rules, Tests and CI: "Every PR: Biome, typecheck, Vitest, Drizzle migration check, Playwright smoke suite. Full Playwright nightly on `dev`. Supabase local runs in CI; e2e hits a real Postgres, never a mock." Roadmap 2026-10-16: "Two branches, dev and main, both protected, nothing pushed directly." Roadmap 2026-10-22: "No `npm audit` gate in CI."

**Hands.** Team runs it, except A7: the Nookkeeper hands L a `gh api` command block for the protection rules once the first green run has named the checks, and L runs it in Git Bash. The Nookkeeper does not report A7 done until L confirms.

**Browse.** Stack up locally. Run the one local gate command from A8 and see every gate pass. Add a throwaway column to `src/db/schema.ts`, run `npm run db:check`, see it fail, revert. Run `npm run test:e2e` and watch the Mailpit sign-in test pass; open Mailpit at `http://127.0.0.1:54324` and see the mail it used. On GitHub, open the PR's Checks tab: every check named and green; open the e2e job's log and find the Supabase start and the sign-in test. Fire the nightly by hand (`gh workflow run <nightly>` on `dev` after merge, or from the Actions tab) and see three browsers pass. After A7, try `gh pr merge` on a PR with a check still running and get refused.

**QA model.** Opus. No production code path changes; the harness is test-only. If the plan ends up touching an auth route to make A3 or A4 work, the Nookkeeper bumps this to Fable at plan review.

**Out of scope.** Fixtures and anything under `supabase/seed` (Ch 0.4–0.6). A Drizzle runtime client for the app (its Deferral stands; A5's driver is test-only). Seeding users in `seed.sql`; the harness makes its own. An `npm audit` gate. Vercel, previews, deploy. Dependabot or Renovate. Coverage thresholds. The browser matrix on PRs. A smoke/full split by tag: the whole suite is the smoke suite until it is slow. Windows runners. Caching Supabase's Docker images.

## 1. Feasibility (Nookkeeper)

- **Supabase in the runner.** `ubuntu-latest` has Docker. The CLI is a pinned devDependency (`supabase` 2.121.0, `docs/STACK.md`), so `npx supabase start` after `npm ci` needs no setup action. Cold start pulls every image, two to four minutes; `-x` excludes services the gates don't use (studio, imgproxy, edge-runtime, logflare, vector, realtime, storage-api are candidates). Auth, Postgres, Kong, PostgREST and Mailpit must stay: the app signs in through Kong and the mail lands in Mailpit. The exact exclusion list is the Cartographer's, verified against `supabase/config.toml`, and the `[api] schemas` setting (Ch 0.2 Q1) is untouched by it.
- **Env in CI is `.env.example`.** Ch 0.2 A1 established that a fresh clone runs with only `.env.example` copied to `.env.local`. CI does the same copy; the publishable key in it is the CLI's fixed local default, not a secret. A5 adds `DATABASE_URL` to `.env.example` as the local default `postgresql://postgres:postgres@127.0.0.1:54322/postgres` (`[db] port = 54322`, config.toml:39). The Ch 0.2 Deferral for `DATABASE_URL` is half-closed by this; the runtime client half stays.
- **The magic link is PKCE, so the page that asks must be the page that clicks.** `tests/e2e/rummage-magic-link-csrf.spec.ts` documents it: requesting a link sets a PKCE verifier cookie, and `/api/v1/auth/callback` exchanges the code against it. A3's test must submit the form from the Playwright `page` (or use `page.request`, which shares the context's cookies), then navigate that same page to the link from Mailpit. A separate `APIRequestContext` will get a 4xx at the callback. This is the step most likely to need a second try.
- **Mailpit's API.** Supabase CLI 2.121 ships Mailpit (`[local_smtp]`, config.toml:111, port 54324; README line 18 names it). Its HTTP API lists messages (`/api/v1/messages`, `/api/v1/search?query=to:<address>`) and returns a message's body by id. The link in the body is Supabase's `/auth/v1/verify?...&redirect_to=http://localhost:3000/api/v1/auth/callback` (the one URL in `additional_redirect_urls`, config.toml:169). Risk: Mailpit's search can lag the send by a beat; the test polls with a short timeout rather than reading once. The Cartographer confirms the endpoint shapes against the pinned CLI's Mailpit version.
- **The fixture, A4.** One sign-in per Playwright worker, saved as `storageState`, is the standard shape and keeps later chapters' suites from paying the mail round-trip per test. Unique addresses (`<run>-<worker>@example.com`) keep workers from reading each other's mail. The Cartographer decides worker-scoped vs test-scoped; the spec cares that a later chapter imports one thing.
- **`npm run dev` vs `npm run build && npm run start` in CI.** `playwright.config.ts` has `webServer: npm run dev` with `reuseExistingServer`. Dev mode in CI compiles on first hit and `next typegen` runs anyway for typecheck; a production build is slower to start but deterministic. The Cartographer picks, likely by `process.env.CI`. `tests/e2e/rummage-graphql-exposure.spec.ts` toggles `pg_graphql` in the database and needs no app restart either way.
- **Playwright browsers.** `npx playwright install --with-deps chromium` on the PR job; all three on the nightly. Cache keyed on `@playwright/test` 1.64.1 so the install is a restore on most runs. WebKit on Linux is supported by Playwright's own deps step.
- **The database test, A5.** `profiles` is not reachable through the Data API (`schemas` without `public`), so the test needs a Postgres driver. A test-only devDependency (`postgres`, porsager, or `pg`) with a STACK.md row; it is not the app's runtime client, which stays deferred to the first chapter that queries an app table. Signing the user up is `signInWithOtp` from `@supabase/supabase-js` against the local stack; README line 18 confirms the account exists before the link is clicked, so no mail reading is needed here. Vitest's `include` is `tests/unit/**` (`vitest.config.ts`); `tests/db/**` gets its own config or project so `npm test` stays stack-free.
- **The migration check, A2.** `drizzle-kit check` reads `supabase/migrations/meta`. The drift half is `drizzle-kit generate` followed by `git status --porcelain supabase/migrations` being empty, which is what the Ch 0.2 handoff ran by hand at Step 5 ("drizzle no changes"). Risk: `generate` with no `--name` prompts in some versions; the script passes a throwaway name and the empty-diff check is what matters. `.claude/skills/migrations/SKILL.md` should name `db:check`; that is a knowledge change for the Scribe or the Afterword.
- **Protection, A7.** Required status checks must name jobs that have run at least once, so the command block comes after the first green run. `gh api -X PUT repos/WilliM233/fluxnook/branches/<branch>/protection` with `required_status_checks.contexts` set to the PR workflow's job names, on both `dev` and `main`; the `dev` to `main` Volume-close PR triggers the same workflow because A1 lists both branches. `gh` is on L's Git Bash PATH, not in the Nookkeeper's shell.
- **Nightly on `dev`.** `schedule` fires only on the default branch; `dev` is the default (Ch 0.2 PR note). `workflow_dispatch` alongside it is what the Browse uses. Pick an off-hour UTC minute that is not :00.
- **Windows-authored, Linux-run.** `.gitattributes` has been committed since Ch 0.1 and Biome handles line endings; the `supabase` npm package downloads the platform binary at install, so any node_modules cache is keyed on the runner OS. Nothing in `tests/` reads a Windows path today (checked: `tests/e2e/*.spec.ts`, `tests/unit/*.test.ts`).
- **House Rules line to fix in this chapter's Afterword, not now.** Tests and CI says fixtures live in `supabase/seed` "from Volume 0 Chapter 3"; after the 2026-10-22 Roadmap calls that is Chapters 4 to 6. Only the Afterword edits House Rules.
- **Runtime budget.** Supabase start plus Playwright install plus a build is six to eight minutes cold; under ten is the target. Over fifteen is a Deferral trigger for the smoke/full split, not a reason to drop a gate.

## 3. Steps (Cartographer)

**Shape choices** (one line why each).

- One job per gate, named as its npm script (`lint`, `typecheck`, `test`, `db:check`, `test:db`, `test:e2e`): the Checks tab and A7's required contexts are the six gate names with nothing to open. `test:db` and `test:e2e` each start their own stack; the two starts run in parallel, so it costs runner minutes (free on a public repo), not wall time.
- Two composite actions under `.github/actions/`, `install` (Node and `npm ci`) and `stack` (env copy and `supabase start -x …`), so the pins and the exclusion list live in one place each for six jobs and the nightly. Composite `run` steps need `shell: bash`.
- `.nvmrc` holds `22.15.0`; both workflows read it with `node-version-file`, and STACK.md's Node row points at it.
- `db:check` is `scripts/db-check.mjs`: `drizzle-kit check` on the real folder, then a copy of `supabase/migrations` under `node_modules/.cache/db-check/`, `generate` against the copy (`DRIZZLE_OUT`, one env read in `drizzle.config.ts`), and a failure when the copy gained a file, printing the SQL that would have been written. The repo is never written to, so the Browse's "see it fail, revert" is the one `schema.ts` line. `.mjs` because Node 22.15 can't run `.mts` without a flag; Biome lints it, `tsc` doesn't.
- Playwright under `process.env.CI`: `webServer` is `npm run start` with `reuseExistingServer: false`, and the job runs `npm run build` as its own step first. A production server is deterministic, a build failure fails on its own line, and the `webServer` timeout stays the default. Locally nothing changes.
- `retries: 0` everywhere: a test that needs a retry is a finding, not a pass (House Rules, Tests and CI). `forbidOnly` in CI, `trace: "retain-on-failure"`, and the HTML report uploaded as an artifact when a job fails, so a red run can be read without re-running.
- Browser matrix by env: `PLAYWRIGHT_ALL_BROWSERS=1` adds Firefox and WebKit to the projects. `npm run test:e2e` stays Chromium locally with one browser installed; the nightly sets the variable and runs one job per browser with `--project`, each on its own stack.
- Harness files under `tests/e2e/harness/` (not `fixtures/`: in this repo a fixture is acceptance data): `mailpit.ts` and `signed-in.ts`. The fixture is `signedIn` and yields `{ page, email }`; a spec imports `test` and `expect` from `./harness/signed-in`. It asks for the link with `page.request.post`, which shares the context's cookie jar, so the PKCE verifier is there when the page follows the link; not the form, so a copy change on the form never breaks every signed-in test. The form stays covered by `sign-in.spec.ts` and the Browse.
- The link comes from Mailpit's `Text` body (one regex, no entity decoding), polled with `expect.poll` for up to ten seconds.
- The db test keys on its own fresh address: `auth.users` by email, then `profiles` by that id. It holds on any database state, so it doesn't reset; CI's stack is fresh after `start`, and the Browse's `db reset` is the by-hand version of the same.
- `npm run check` runs the six gates in A1's order joined by `&&`, which `sh` and `cmd` both understand.
- `concurrency` cancels a stale run when the branch is pushed again; `permissions: contents: read` because nothing writes.
- Nightly at `17 4 * * *` UTC: not :00, and off-hours for L.
